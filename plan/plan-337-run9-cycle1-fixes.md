## Item 1 — AGG-C4-01: touch-target audit scale-token regex false-positives on `max-h-{1..10}` / `max-w-{1..10}` (MED · critic · the substantive test-gate fix)

- **Source:** CRT-1 (critic, High confidence; ORCHESTRATOR-VERIFIED empirically in Node against the exact committed regex).
- **Where:** `apps/web/src/__tests__/touch-target-audit.test.ts:342,346,350,354` — the four scale-token patterns added by `d70c1d98`. Each alternates `(?:min-h|min-w|size|h|w)-(?:[1-9]|10)` where the bare `h`/`w` branches are preceded only by `\b`.
- **Why it matters:** `\bh-10\b` matches the `h-10` substring INSIDE `max-h-10`, and `\bw-9\b` inside `max-w-9`. Verified: `<Button className="max-h-10">` and `<Button className="max-w-9">` both FLAG as "renders ≤40 px below 44 px floor" — FALSE, because `max-height`/`max-width` are CEILINGS, not floors, and never constrain the tap target. The gate is green TODAY only because no current `<Button>` uses `max-h-{1..10}`/`max-w-{1..10}`. The moment a legitimate one is added, the blocking gate fires with a lying message, training developers to silence it with a bogus `min-h-11` override — which defeats the entire audit. The `min-h`/`min-w`/`size` branches are CORRECT (those ARE floors); only the bare `h`/`w` branches are buggy. test-engineer separately confirmed the larger-token `\b` boundaries are correct (`h-14`/`size-16`/`min-h-20` are NOT flagged), so the bug is narrowed to exactly the `max-` prefix.
- **Change:**
  1. Anchor the bare `h`/`w` branches in all four patterns so they do NOT match after a `max-`/`min-`/`size-`-style prefix. The cleanest fix is a negative lookbehind on the bare-token branches: split the alternation so `min-h|min-w|size` keep their current `\b` anchor, and the bare `h|w` branches get `(?<!\w-)` OR an explicit `(?<!max-)(?<!min-)` (note `min-h`/`min-w` are already separate branches, so the bare `h`/`w` must reject `max-h`/`max-w`). Simplest robust form: replace the bare `h`/`w` branch boundary so it requires the `h`/`w` to be preceded by a className-start or whitespace, not a `-`. E.g. change `\b(?:min-h|min-w|size|h|w)-` to `(?:\b(?:min-h|min-w|size)-|(?<![\w-])(?:h|w)-)` — the `(?<![\w-])` prevents matching `h`/`w` that follow a `-` (as in `max-h`, `min-h` already covered) or a word char.
  2. Add SELF-CHECK assertions in the test file (a `describe('scale-token regex self-check')` block) that prove, against each of the four patterns: `max-h-10` / `max-w-9` / `max-h-screen` are NOT flagged, while `h-8` / `min-h-6` / `size-9` ARE flagged, and `min-h-11` / `h-14` / `size-16` are NOT flagged. This pins the fix so a future regex edit can't silently re-introduce the false positive.
- **Acceptance:** the four patterns no longer match `max-h-{1..10}`/`max-w-{1..10}` but still match the real sub-44 scale tokens (`h-8`, `min-h-6`, `size-9`); the new self-check block passes; the full `touch-target-audit.test.ts` still passes (no current file regresses); `npm test --workspace=apps/web` green. Run `npm run typecheck` before committing the test change.

## Item 2 — AGG-C4-02: sidecar backfill `flushBatch` lacks the `affectedRows` orphan-cleanup guard (MED · architect · the production-path data-hygiene fix)

- **Source:** ARCH-R9-01 (architect, High confidence; mechanism verified by orchestrator — sidecar has no `affectedRows` check).
- **Where:** `apps/web/scripts/backfill-color-pipeline.ts:318-342` — the `flushBatch` function runs `tx.execute(sql\`UPDATE images SET … WHERE id = ${item.id}\`)` in a batched transaction loop with NO `affectedRows` check and NO derivative cleanup.
- **Why it matters:** the in-app `admin-backfill-runner.ts` got the AGG-R8c3-03 fix (both branches guard `affectedRows===0 → cleanupDeletedMidReencodeVariants`), but its sibling SIDECAR — which CLAUDE.md documents as the canonical PRODUCTION backfill (the prod runtime container lacks `tsx` + the TS source, so the `--rm` sidecar IS how prod re-encodes) — was NOT updated. Same delete-during-reencode race ⇒ orphaned derivative files for a deleted image on the production path, never cleaned up. CLAUDE.md asserts the two paths are equivalent ("SAME DB column set", "never strand stale color metadata") — that equivalence is now FALSE for the cleanup contract. Admin-only, low-probability (concurrent `deleteImage` during a backfill of the SAME image id; `deleteImage` does NOT acquire the per-image processing lock, so it can interleave), disk-leak only, no corruption.
- **Change:**
  1. In `flushBatch`, capture each UPDATE's ResultSetHeader: `const [res] = await tx.execute(sql\`UPDATE … WHERE id = ${item.id}\`);` (match the destructure shape the codebase already uses — `image-queue.ts` reads `[updateResult]` from `db.update(...)`; for `tx.execute(sql\`…\`)` the ResultSetHeader is the first tuple element).
  2. If `res.affectedRows === 0` (row deleted mid-reencode), clean up the just-written derivative files the same way the runner does — call the shared cleanup with `sizes=[]` (full dir scan) for webp/avif/jpeg using the script's existing variant-dir + filename access. The script already imports/derives the per-format dirs and filenames it writes; reuse `deleteImageVariants(dir, fn, [])` from `@/lib/process-image` (the script imports from the source tree). Track the count in a `deletedMidReencode` tally and log it in the run summary alongside processed/skipped/failed (mirror the runner's outcome partitioning — `deleted-mid-reencode` is NEITHER a success NOR an encode failure).
  3. NOTE: `flushBatch` updates in a single `db.transaction`. The cleanup unlink is best-effort filesystem I/O — perform it AFTER the transaction commits (collect the ids whose UPDATE returned `affectedRows===0` during the tx, then unlink their variants outside the tx) so a filesystem error can't roll back legitimate DB updates for sibling rows in the same batch.
- **Acceptance:** the sidecar `flushBatch` checks `affectedRows` on every UPDATE and cleans up derivatives (dir-scan) for any row deleted mid-reencode, with a `deletedMidReencode` tally in the summary. Because the sidecar is a `scripts/` JS/TS file (covered by `typecheck:scripts`, not vitest), the verification is: `npm run typecheck --workspace=apps/web` green + manual reasoning that the cleanup mirrors `admin-backfill-runner.ts`'s `cleanupDeletedMidReencodeVariants` semantics (the runner's behavior is already unit-tested; the sidecar shares the same `deleteImageVariants(dir, fn, [])` primitive). Add a note in CLAUDE.md's Backfill section that BOTH paths now carry the cleanup guard (closes the doc-equivalence claim). Full gate run green.

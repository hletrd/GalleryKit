## ARCH-C9-01 [MEDIUM, confidence H] — AGG-C8-02 fix is incomplete: downloader manifest omits the two FATAL config JSONs the offline loader requires

**Where:**
- `apps/web/scripts/clip-model-manifest.ts:25-30` — `CLIP_MODEL_MANIFEST` has exactly two entries: `onnx/model_quantized.onnx` and `tokenizer.json`. The doc comment (lines 21-23) deliberately excludes config/tokenizer JSON ("small and self-describing").
- `apps/web/scripts/download-clip-models.ts:72-84` — the cycle-8 AGG-C8-02 fast-path calls `verifyAndCleanArtifacts(modelCacheDir, MANIFEST, /*deleteOnMismatch*/ false)` and short-circuits ("already up to date") iff `preCheck.ok`. `verifyAndCleanArtifacts` (`clip-model-manifest.ts:71`) iterates only `Object.entries(manifest)` — so "full manifest" means full coverage of the 2-entry constant, NOT the full fatal-file set.
- `apps/web/src/lib/clip-model.ts:90-98` — `AutoModel.from_pretrained` (loads `config.json`) then `AutoTokenizer.from_pretrained` (loads `tokenizer.json` + `tokenizer_config.json`), both with `env.allowRemoteModels=false`.

**Verified against installed transformers v3 source (`node_modules/@huggingface/transformers/src/`):**
- `configs.js:54` — `getModelJSON(pretrained_model_name_or_path, 'config.json', true, options)` — the `true` is `fatal`. `AutoConfig.from_pretrained` is called at `models.js:1141`, so a missing `config.json` under `allowRemoteModels=false` THROWS.
- `tokenizers.js:70-71` — `loadTokenizer` loads BOTH `tokenizer.json` AND `tokenizer_config.json` with `fatal=true`. `AutoTokenizer.from_pretrained` THROWS if either is missing offline.
- `hub.js:535-538` — when `!env.allowRemoteModels` and the file is not found locally and `fatal`, it throws `` `env.allowRemoteModels=false` ... file was not found locally ``.
- `preprocessor_config.json` is NOT in the fatal set here: `embedImageReal` (`clip-model.ts:151-200`) does manual Sharp preprocessing + builds the `Tensor` by hand — it never calls `AutoProcessor`/`AutoImageProcessor`. Confirmed: the fatal set is exactly `{config.json, tokenizer_config.json, tokenizer.json, onnx/model_quantized.onnx}`; the manifest covers 2 of the 4.

**Architectural problem:** the seed→offline-load contract has a single source of truth for "what must be present on the volume" — the manifest. But the SET the downloader verifies (`{onnx, tokenizer.json}`) is a strict subset of the SET the runtime loader treats as fatal (`{onnx, tokenizer.json, config.json, tokenizer_config.json}`). The two ends of the contract disagree on the required-file set. The cycle-8 fix correctly widened the fast-path from ONNX-only to "the manifest", but the manifest itself was never widened to the fatal set — so the gap moved from `{tokenizer.json, config.json, tokenizer_config.json}` down to `{config.json, tokenizer_config.json}` rather than closing.

**Risk scenario:** an operator's seed is interrupted, or a `config.json`/`tokenizer_config.json` is truncated/corrupted on the bind-mount (partial copy, fs error, rsync abort) while ONNX + tokenizer.json are intact. Re-running `download-clip-models.ts` prints "All checksums OK — already up to date. Nothing to do." and exits 0 across every retry. The first production `/api/search/semantic` (or `/api/search/similar/[id]`) query then throws in `from_pretrained`, the `catch` at `clip-model.ts:101-105` nulls `loadPromise`, the route's embed `try` (`semantic/route.ts:240-245`) returns 503, and EVERY subsequent semantic/similar request 503s indefinitely — the idempotency gate that is supposed to PREVENT this green-lights it. This is the same operational blast radius the 4-agent-consensus AGG-C8-02 rated HIGH, on a now-LIVE path.

**Why MEDIUM (not HIGH like AGG-C8-02):** the trigger is narrower than the original — it requires the two SMALL config JSONs specifically to be the corrupt/missing ones while the large ONNX + tokenizer.json survive. In practice `Transformers.js` downloads all four in one `from_pretrained`, so a clean HF download lands all four atomically-ish; the partial-config scenario is most plausible under a hand-rolled volume copy or a truncated-on-disk corruption. Operator-side seed surface, single deployment behind the double-gate. But it IS a real residual of a finding rated HIGH, on a LIVE availability path, and the fix is trivial — so it should not be silently absorbed.

**Fix/direction (cheap, additive, low-risk):** add `config.json` and `tokenizer_config.json` to `CLIP_MODEL_MANIFEST` with their pinned-revision SHA-256s (obtainable from the same Task-1 spike download / `huggingface.co/api/models/jinaai/jina-clip-v2` at revision `e10d47f5...`). The existing `verifyAndCleanArtifacts` loop then covers them automatically in BOTH the fast-path inspection and the post-download verify, re-aligning the verified set with the loader's fatal set. Update the manifest doc comment (lines 21-23) to state the manifest must mirror the offline loader's fatal-file set, not just "expensive binaries". Add a Vitest asserting the manifest keys are a superset of `{config.json, tokenizer_config.json, tokenizer.json, onnx/model_quantized.onnx}` so a future model upgrade that adds a fatal file fails loud. (If pinning the JSON SHAs is judged too brittle across benign HF metadata reformatting, the alternative is an existence-only check for the two config files in the fast-path — weaker, but still closes the "missing file reported up-to-date" hole.)

## Consensus / antithesis note
Strongest argument AGAINST ARCH-C9-01 being worth acting on: the cycle-8 test + register treated AGG-C8-02 as closed, and a clean HF `from_pretrained` lands all four files together, so the partial-config window is narrow. Counter (why it still merits a fix): the finding's whole POINT was that the idempotency gate must not green-light a seed the runtime then rejects as fatal — and against the installed transformers source, `config.json` + `tokenizer_config.json` ARE fatal and ARE NOT verified. The fix is ~2 manifest lines + a superset test; leaving a known subset/fatal-set mismatch in the single-source-of-truth contract is exactly the kind of silent drift the migration/manifest discipline elsewhere in this repo exists to prevent. Tradeoff tension: pinning JSON SHAs adds a re-pin step on model upgrade (already required for the ONNX SHA + revision, so marginal) vs. the weaker existence-only check that avoids SHA brittleness but doesn't catch a same-size corruption.

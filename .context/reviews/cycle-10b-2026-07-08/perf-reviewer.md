## New finding

### PERF10B-01 — `deleteImages` now performs N sequential single-row INSERTs inside its delete transaction (regression traded in for the new durable-cleanup feature)

- **Severity:** Medium · **Confidence:** High
- **Where:** `apps/web/src/app/actions/images.ts:808-836` (the `deleteImages` batch-delete transaction), for context compare the single-image path at `apps/web/src/app/actions/images.ts:674-694` (`deleteImage`, only ever inserts one row so it isn't affected the same way).
- **What it is:** Cycle 21 of the peer run-10 lineage (commit `8b795862`, "fix(cycle21)") added a `pending_file_deletions` durability table so a post-DB-delete filesystem cleanup failure is retryable (`apps/web/src/lib/pending-file-deletions.ts`, `apps/web/src/db/schema.ts:134-153`) — a real reliability improvement, not being re-litigated here. To get each row's own `pending_file_deletions.id` back for later retry bookkeeping, `deleteImages` does:
  ```ts
  await db.transaction(async (tx) => {
      for (const image of imageRecords) {                       // images.ts:815
          const [pendingResult] = await tx.insert(pendingFileDeletions).values({...});  // images.ts:816
          pendingDeletions.push({ id: safeInsertId(pendingResult.insertId), ... });      // images.ts:823
      }
      await tx.delete(imageTags).where(inArray(imageTags.imageId, foundIds));            // images.ts:832
      const [deleteResult] = await tx.delete(images).where(inArray(images.id, foundIds)); // images.ts:833
  });
  ```
  This is a sequential `await`-in-a-`for`-loop — one full network round trip to MySQL per image in the batch, all executed one after another before the two batched `DELETE`s even run, all inside the same transaction.
- **Why it hurts:** batch delete is capped at 100 images (`images.ts:754-756`, `if (ids.length > 100) return { error: t('tooManyImages') }`), so a full-batch delete now issues up to 100 sequential single-row `INSERT`s where one multi-row `INSERT` (or none, per the fix below) would do. Concretely:
  - The transaction's critical section — during which it holds one pooled MySQL connection and, once the two `DELETE`s execute, row/gap locks on `images`/`imageTags` — is extended by up to ~100 sequential round trips before those `DELETE`s even start. At same-host MySQL latency (this repo's shipped `network_mode: host` compose topology) each round trip is sub-millisecond, so the direct wall-clock cost is modest (tens of ms); on a remote/managed MySQL host with 1-5 ms RTT it becomes ~100-500 ms of extra transaction-open time per full-batch delete.
  - This runs directly counter to the pool-budget discipline this repo documents everywhere else (CLAUDE.md's "Database Indexes" section explicitly reasons about extra pinned connections/lock windows during concurrent admin mutations, e.g. the topic-route-mutation lock and in-flight DB-restore connection accounting). A 100-image bulk delete now pins its pool connection, and the `images`/`imageTags` locks once it reaches the `DELETE`s, for a needlessly longer window — worst under concurrent admin activity (e.g., another admin mutating the same topic's images, or a live page's `getImage()` `Promise.all` fan-out queueing behind the held locks).
  - It is a genuine behavior change versus the pre-cycle-21 code path (which deleted the DB rows first with no per-row insert loop, then fired cleanup in parallel) — i.e., a real perf cost newly introduced as a side effect of the reliability fix, not something already tracked by the peer lineage's cycle 21-29 perf/architect reviews (`run10-cycle27/28/29`) or by loop-B's own cycle-9 perf pass, none of which mention `pendingFileDeletions`/`deleteImages` insert-loop cost.
- **Fix:** avoid needing the per-row ID inside the transaction at all. Do a single multi-row `INSERT INTO pending_file_deletions (...) VALUES (...), (...), ...` (Drizzle's `tx.insert(pendingFileDeletions).values([...])` accepts an array), then — either inside the same transaction or immediately after commit — issue **one** `SELECT id, image_id, filename_original, filename_webp, filename_avif, filename_jpeg FROM pending_file_deletions WHERE image_id IN (${foundIds})` to recover the per-row ids needed for later cleanup bookkeeping. That collapses the N-insert loop plus the current 0 extra selects into 1 insert + 1 select, independent of batch size. (A cheaper but subtler alternative — computing `id = firstInsertId + index` from the single multi-row insert's returned `insertId`, relying on MySQL's documented single-statement AUTO_INCREMENT contiguity guarantee even under the default `innodb_autoincrement_lock_mode=2` — works too, but the read-back-by-`image_id` approach doesn't depend on that subtlety and is safer to review.)
- **Trade-off:** the fix trades one extra round trip (the read-back `SELECT`) for eliminating up to 99 others — strictly a net win at any batch size ≥ 2, with no loss of the newly added durability guarantee (the pending rows are still committed in the same transaction as the image/tag deletes either way).
- **Not re-flagged:** the single-image `deleteImage` path (`images.ts:674-694`) and the bounded post-transaction file-cleanup concurrency (`CLEANUP_CONCURRENCY`-chunked `Promise.all` over `cleanupPendingFileDeletion`, unchanged shape from before cycle 21) are unaffected — only the batch path's pre-`DELETE` insert loop is new and in scope here.

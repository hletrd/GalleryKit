## Findings

### C7-TR1 — Per-image and DB-restore advisory-lock cleanup still releases (not destroys) a connection after a failed RELEASE_LOCK
[SEV: HIGH | CONF: High (code defect) / Medium (real-world trigger frequency) | category: concurrency / resource-leak]

**Files + lines:**
- `apps/web/src/lib/image-queue.ts:659-667` (`releaseImageProcessingClaim`)
- `apps/web/src/lib/admin-backfill-runner.ts:381-387` (duplicate helper, same name)
- `apps/web/src/app/[locale]/admin/db-actions.ts:389-394` (backup path) and `:585-647` (restore path; RELEASE_LOCK call sites at 390, 449, 462, 481, 485, 519, 524, 530, 606, 611, 617, 633, 638, 643, unconditional `conn.release()` at 394 / 647)
- `apps/web/src/lib/upload-processing-contract-lock.ts:44-56` (same shape, lower priority — same file also has a correctly-defensive branch at lines 57-73 for the GET_LOCK-throws case, but not for the release()-after-lock-acquired case)

**Why it's a problem:** MySQL `GET_LOCK`/`RELEASE_LOCK` are session-scoped. If the `RELEASE_LOCK` query itself fails (transient network blip, brief server hiccup, anything that errors the query without killing the TCP session), the code swallows or logs the error and then unconditionally returns the connection to the pool (`conn.release()`/`lockConnection.release()`). The connection is fully functional for ordinary queries afterward — no crash, no visible corruption — but its underlying MySQL session silently continues to hold the named advisory lock forever (until the process restarts and the pool is torn down). `3acf638a` ("harden mutation lock cleanup") fixed exactly this pattern in `apps/web/src/app/actions/topics.ts` by tracking a `releaseCleanly` flag and calling `conn.destroy()` instead when release fails — but did not touch the structurally identical code in the four locations above.

**Concrete failure scenarios:**
1. Image id 42 finishes processing successfully (`processed=true` committed). In the `finally` block, `RELEASE_LOCK('gallerykit:image-processing:42')` transiently fails. The connection returns to the pool still "holding" that lock. Weeks later, an admin runs "re-encode existing photos" (color-pipeline backfill) — every image except id 42 succeeds; id 42 silently fails to acquire its claim on every attempt, forever, with only a debug/error log line to explain why (`admin-backfill-runner.ts` / `image-queue.ts:739`'s misleading "another worker may still hold" message, since no other worker actually does).
2. `LOCK_DB_RESTORE` is checked with `GET_LOCK(..., 0)` (non-blocking) as a global mutex for *every* future backup and restore attempt. If any of the ~7 `RELEASE_LOCK` calls in the restore/backup finally-blocks fails once, the connection returns to the pool still holding `gallerykit_db_restore`. From that point on, every subsequent backup AND restore attempt immediately fails with `restoreInProgress`/`restoreBlockedBy...` — a full, silent outage of the backup/restore admin feature until the web process is restarted. Nothing else in the app is visibly broken, so this could be mistaken for "someone left a restore running" when no restore is actually in progress.

**Suggested fix:** Extract the `releaseCleanly`-flag + `conn.destroy()`-on-failure pattern already proven in `topics.ts` (3acf638a) into a small shared helper (e.g. `releaseLockConnection(conn, releasedCleanly)`), and apply it at every `RELEASE_LOCK` call site listed above — in `db-actions.ts` specifically, track one boolean across the whole function (any release failure taints the final `conn.release()`/`conn.destroy()` decision) since all locks share one connection there.

**Status:** Likely (confirmed via direct code + mysql2 library semantics reading; live-incident trigger not reproduced — see Discriminating Probe).

### C7-TR2 — Restore-window logout skips server-side session revocation while still clearing the client cookie
[SEV: MED | CONF: Medium | category: security / session management]

**File + lines:** `apps/web/src/app/actions/auth.ts:277-292` (introduced by `3acf638a`)

**Why it's a problem:** Before `3acf638a`, `logout()` unconditionally executed `db.delete(sessions).where(eq(sessions.id, hashSessionToken(token)))` (and the audit-log write) on every call. The commit correctly fences this DB mutation behind the restore-maintenance marker + `acquireAdminMutationSlot()` (matching every other mutating admin action's contract) to stop it racing a live restore import — but the fencing means that during any restore-maintenance window (which can run long for large dumps per the repo's own `C3-31` deferred note), the session row is **not deleted at all**, while `cookieStore.delete(...)` still runs unconditionally afterward. `purgeExpiredSessions()` (`maintenance-scheduler.ts:16-18`) only removes rows whose `expiresAt < NOW()` — there is no "pending revoke" retry, so a session whose logout was skipped remains fully valid server-side for its entire remaining TTL, independent of when the restore ends.

**Concrete failure scenario:** An admin's session token is compromised (device left unlocked, log/proxy leak, etc.). The legitimate admin clicks "Log out" while a DB restore happens to be in progress. Their own browser's cookie is cleared (they believe they are logged out), but the session row backing the stolen token is never deleted. The attacker can continue using the stolen token for as long as it remains within its original TTL — the restore window doesn't even need to still be active; nothing ever revisits this session once the restore ends.

**Suggested fix:** Either (a) exempt the single, narrowly-scoped keyed `DELETE ... WHERE id = <hash>` from the mutation barrier (its blast radius against a concurrent restore is a no-op or a row that the restore replaces anyway, unlike broader admin mutations), executing it unconditionally as before, while keeping the *audit-log write* fenced if desired; or (b) if the fence must cover the delete too, queue the skipped revocation (e.g., a small in-memory/durable "pending session revocations" list) and flush it when `endDurableRestoreMaintenance()` runs, so the token's server-side validity actually ends shortly after the restore completes rather than silently surviving to natural TTL expiry.

**Status:** Likely (confirmed via diff + code reading; not exercised against a live restore + logout race).

### CRIT3-02 — The same commit exempts the on-the-fly image optimizer from the new limiter, leaving the one CPU+disk-heavy public endpoint unthrottled on a disk-fragile host
- Severity: Med-Low. Confidence: Medium. Perspective: attacker / operator. Class: DoS residual / fix-opens-adjacent-gap.
- Evidence:
  - `af3b2f7d` adds `location ^~ /_next/image { proxy_pass ... }` with **no** `limit_req`, deliberately carving `/_next/image` out of the `public` zone (comment: "must stay outside the public page limiter, or a normal cold-cache page load could exhaust a per-IP burst by itself").
  - next/image IS active: `next.config.ts:117` sets `images: { formats, localPatterns, remotePatterns }` with **no `unoptimized`**; `src/components/optimistic-image.tsx:58` renders `<Image>` from `next/image` with no per-instance `unoptimized`, and it is the masonry grid's tile renderer (`masonry-card.tsx` → `OptimisticImage`). So a normal gallery paint fans out many `/_next/image?url=/uploads/...&w=...` requests, each of which runs a Sharp resize and writes a `.next/cache/images` entry on first hit.
  - CLAUDE.md's Operational Playbook documents a real, repeated host disk-exhaustion history (the 2026-06-17 "userspace starvation past SSH recovery" incident).
- Why it matters: the fix protects the DB pool but leaves the single most CPU- and disk-write-intensive public path with **no limiter of its own**. An actor enumerating `/_next/image` over (distinct upload url × allowlisted width) tuples burns Sharp CPU and grows the on-disk image cache — the exact resource (host disk) the playbook flags as the deployment's Achilles heel. The DoS surface is bounded (Next rejects non-allowlisted `w`, and caches by tuple) but grows with gallery size and is entirely unthrottled at the edge.
- Failure scenario: a scraper hits `/_next/image` for every derivative × every device/image size; CPU spikes and `.next/cache/images` grows on the writable layer; combined with the documented builder-cache growth, the host trends toward the 100%-disk wedge that once required a block-volume resize to recover.
- Suggested fix: give `/_next/image` its own **looser** `limit_req zone=nextimage rate=30r/s burst=120 nodelay` (generous enough for a legit cold paint, still a per-IP flood cap) rather than a blanket exemption; OR document the residual explicitly so it is a stated operator boundary, not an implied-covered surface. Full exemption + "public surface rate-limited" in the ledger is the same false-coverage shape CRIT-01/CRIT-03 flagged, one layer down.

### CRIT3-03 — migrate.js's mixed-state path silently swallows a new migration's SQL with only a console.warn, disarming the very fail-loud post-condition the hardening exists for
- Severity: Medium. Confidence: Medium (the code path is exact; reachability requires a drift+new-tail DB, which is uncommon but is precisely the historical incident class). Perspective: correctness / future maintainer. Class: narrowed-but-not-closed silent-skip.
- Evidence (`apps/web/scripts/migrate.js:764-838`):
  - The `b4e986c3` fix correctly adds a PENDING fast-path (`:812-816`): when every missing hash sits strictly ABOVE `MAX(created_at)`, it returns without baselining so `drizzle.migrate()` genuinely applies the SQL. That case is now correct.
  - But the MIXED case remains: when `missing` contains any at/below-cursor entry (real drift) AND a correctly-authored new tail above the cursor, `missing.every(> cursor)` is false, so control falls to `:827-837`: it prints a `console.warn` naming the `swallowedTail`, then runs `reconcileLegacySchema` (DDL-only) + `baselineAllJournalMigrations` (records ALL hashes, including the tail's).
  - Consequence: the new tail migration's `.sql` **never executes** (reconcile mirrors DDL, never DML), yet its hash is recorded — so the loud `runMigrations` post-condition ("every journal hash present, else throw") sees the hash present and **does not fire**. The deploy exits 0. Only a `console.warn` in the deploy log distinguishes this from a healthy run.
- Why it matters: the entire migrate.js hardening (CLAUDE.md "Migration & Schema-Drift Runbook") was built because drizzle silently skipped migrations and "every deploy logged Complete with no error"; the post-condition throw is the safety net. This fix restores the net for the pure-pending case but re-creates a narrower silent-skip for the mixed case — a warn is not a throw, and a warn on "your DML backfill did not run" is easy to miss in a per-iteration deploy log. The mixed state is exactly the drift-carrying production DB the runbook describes.
- Failure scenario: a deployed DB carries pre-existing drift (one un-recorded historical hash) when a new migration with a DML backfill lands; the deploy succeeds; the DDL is present (via reconcile) but the backfill rows are missing; nothing fails; the discrepancy surfaces later as "why is column X populated on fresh installs but null in prod."
- Suggested fix / decision: in the mixed case, **throw** (fail the deploy) instead of `console.warn` — a mixed drift+new-tail state is genuinely ambiguous and shipping it green with lost DML is the worst outcome. Failing loud forces the operator to reconcile the drift, then re-deploy so the tail applies cleanly. (Note the author's implicit reason for baseline-over-apply: reconcile has already created the tail's columns, so letting drizzle apply the tail's non-`IF NOT EXISTS` DDL would throw duplicate-column. That is real — which is why the correct move is to FAIL and require manual resolution, not to auto-baseline.)

### CRIT3-04 — The single-writer guard's advisory lock is not DB-scoped, so it false-alarms (and self-defeats) in the multi-tenant scenario CLAUDE.md itself contemplates, and cries wolf on ordinary restarts
- Severity: Low-Med. Confidence: High. Perspective: operator / doc. Class: reused-footgun + best-effort-guard-defeated.
- Evidence:
  - `advisory-locks.ts:56`: `LOCK_SINGLE_WRITER_GUARD = 'gallerykit_web_singleton'` — a bare, non-namespaced name.
  - CLAUDE.md's "Advisory-lock scope note" (C8R-RPL-06) documents that MySQL advisory-lock names are scoped to the SERVER, not the database, lists every existing lock, and says two GalleryKit instances on one MySQL server "share the same lock namespace… Run one GalleryKit per MySQL server — or prefix advisory-lock names with a per-instance identifier if multi-tenant co-location is required." The new `gallerykit_web_singleton` is **not added to that list** (doc drift) and is **not** per-instance-prefixed.
  - In `single-writer-guard.ts`, the unavailable branch logs the loud "ANOTHER LIVE GALLERYKIT INSTANCE DETECTED" error then `await conn.end()` — so the second instance keeps NO held connection, i.e. it runs with no guard liveness at all.
- Why it matters:
  1. **Multi-tenant false alarm + self-defeat:** two legitimately separate galleries (separate DBs) on one MySQL server — the exact co-location CLAUDE.md says is supported *with namespacing* — will have the second instance permanently log the scary desync error even though it is correctly configured, AND that second instance holds no lock, so the guard is inert for it.
  2. **Cry-wolf on restart:** on a rolling deploy the new container boots while the old one is still in its up-to-15s drain (releases the lock only at the end) → false alarm on ordinary deploys. On an ungraceful kill (SIGKILL/OOM/`docker kill`, exit 137), the lock is not released until MySQL notices the dead connection (up to `wait_timeout`), so the next boot within that window ALSO false-alarms and runs guardless. A guard that fires on normal operations trains operators to ignore it — defeating its only purpose (it is warn-only by design).
- Failure scenario: operator runs two galleries on one MySQL host (namespaced DBs, as documented-supported); instance B logs a red "DATA DESYNC RISK" banner forever; operator either wastes time chasing a non-issue or learns to ignore the banner, so a REAL second-instance-on-same-DB misconfig later goes unheeded.
- Suggested fix: namespace the lock by database name, e.g. `gallerykit_web_singleton:${DB_NAME}` (matches the "per-instance identifier" guidance CLAUDE.md already gives for the other locks), and add the lock to the documented advisory-lock enumeration. Optionally soften the deploy-overlap cry-wolf by probing after a short delay or logging at warn (not error) for the first N seconds of process life.

### CRIT3-05 — The SW warm-path change trades a guaranteed recency refresh for a best-effort one; a meta-write failure can evict an image the server keeps confirming fresh
- Severity: Low. Confidence: Medium. Perspective: correctness / end-user. Class: silent behavior downgrade.
- Evidence (`bf5a4da9`, `sw.template.js`/`sw.js`):
  - Before: the 304 / same-ETag branch called `await refreshCachedImageTimestamp(...)`, which rewrote the cached Response with a fresh `sw-cached-at` header and awaited the `cache.put` — recency advancement was **guaranteed** before the response returned.
  - After: those branches return the cached Response directly and call `touchMeta(request.url, cachedSize).catch(() => {})` — **fire-and-forget, not awaited** — and the `sw-cached-at` header is now frozen (the comment: "the header stops advancing once an entry has been touched this way"). `evictExpiredCachedImage` reads the meta timestamp first, header only as fallback.
  - So the meta store is now the SOLE authority for recency on any touched entry, and its update is best-effort.
- Why it matters: if a `touchMeta` write fails (META_CACHE write error, storage pressure, a racing mutation the `withMetaMutation` serializer drops), the meta timestamp stops advancing AND the header is frozen — so a hot image the server returns 304 for on every view ages out at `IMAGE_MAX_STALE_MS` and is deleted, forcing a full re-fetch. The pre-change awaited header rewrite could not silently fail this way.
- Failure scenario: under cache/storage pressure on a low-end mobile device, meta writes intermittently fail; frequently-viewed thumbnails get evicted despite being server-fresh; the SW re-downloads them, defeating the warm-cache goal the PWA story is built on (low-probability, self-healing).
- Suggested fix: `await` `touchMeta` on the 304/same-ETag branch (it is cheap relative to the removed body rewrite), or keep a lightweight header-only touch as a redundant recency source so a dropped meta write cannot alone age out a confirmed-fresh entry. The body-rewrite removal (the actual perf win) is sound and worth keeping; only the recency-authority downgrade needs a backstop.

### TEST9-01 — The restore drain-checklist orchestration in `restoreDatabase()` is pinned only by source-text scans, never executed

- Severity: High
- Confidence: High
- Location: `apps/web/src/app/[locale]/admin/db-actions.ts:545-609` (the sequential `quiesceImageProcessingQueueForRestore` → `drainBackgroundDbWritesForRestore` → `drainMaintenanceSweepsForRestore` → `drainAdminMutationsForRestore` → abort-or-continue checklist, each followed by `if (!xDrained) return { success: false, ... }`); test evidence in `apps/web/src/__tests__/restore-blocker-messages.test.ts:16-77`, `apps/web/src/__tests__/restore-upload-lock.test.ts:96`, and `apps/web/src/__tests__/image-queue-quiesce.test.ts:15`.
- Evidence: Every test that touches `restoreDatabase` locates code with `source.indexOf('export async function restoreDatabase')` / `readFileSync(...db-actions.ts)` and then asserts on string slices (lock names, `t('restoreBlockedByUpload')`, etc.). No test file ever imports and calls `restoreDatabase()` itself. The four individual drain helpers each have their own unit tests (`background-db-writes.test.ts`, `maintenance-scheduler-source.test.ts`, `admin-mutation-barrier.test.ts`, `image-queue-quiesce.test.ts`), but none of those exercises the ORCHESTRATION in `db-actions.ts` — the exact sequencing and early-return-on-timeout contract that CLAUDE.md calls "a manual drain-checklist... every process-local DB writer MUST be drained here before the import replaces the tables."
- Why this is real: this is the single most safety-critical control-flow in the codebase — a bug here means a DB restore can proceed while a background writer is still mid-commit, silently corrupting the freshly restored data. A `source.indexOf`/string-slice test proves the literal characters exist somewhere in the file; it cannot prove that a timeout from drain #2, #3, or #4 actually short-circuits before `runRestore()` runs, or that the `imageQueueQuiesced` / `restoreLifecycleVerified` / `keepRestoreMaintenance` flags in the `finally` block resolve correctly on every exit path.
- Concrete failure scenario: a future edit reorders the four `if (!xDrained) return {...}` blocks, or someone refactors an early `return` into a `break`/fallthrough that still reaches `runRestore()`, or a maintenance-sweep timeout is silently converted from "abort" to "log and continue." Every existing test (all four drain-helper unit tests, plus the three source-slice tests referencing `restoreDatabase`) keeps passing because none of them ever invoke the function end-to-end. Only a live restore attempt during an in-flight maintenance sweep or admin mutation would discover the regression — in production.
- Suggested fix: extract the checklist into a small, dependency-injected orchestrator function (e.g. `runRestoreDrainChecklist({ quiesceImageQueue, drainBackgroundWrites, drainMaintenanceSweeps, drainAdminMutations })` returning `{ ok: true } | { ok: false, stage: string }`) so a test can inject four mock drains, make each one fail in turn, and assert (a) the checklist stops at the failing stage, (b) later stages never run, and (c) the result maps to the right `restoreFailed`/blocked message. This mirrors how `computeBackfillExitCode` was already extracted out of `backfill-color-pipeline.ts` for testability (see TEST9-05) — the same pattern applies here and is a much stronger regression net than the current string-slice tests, which can stay as a secondary source-contract layer.

### TEST9-02 — GPS-strip fail-closed contract (both upload paths) is asserted only via source-text regex, never executed

- Severity: High
- Confidence: High
- Location: `apps/web/src/app/actions/images.ts` (browser `uploadImages()` GPS-strip guard) and `apps/web/src/app/api/admin/lr/upload/route.ts` (Lightroom PAT upload route); pinned by `apps/web/src/__tests__/images-action-gps-toggle-wiring.test.ts:69-91` and `apps/web/src/__tests__/lr-upload-hdr-gate.test.ts:24-30, 101-105`.
- Evidence: Both test files openly document the trade-off in their own header comments — e.g. `images-action-gps-toggle-wiring.test.ts:14-18`: "A behavioral test would need to mock `getGalleryConfig` + `saveOriginalAndGetMetadata` + `extractExifForDb` + `stripGpsFromOriginal` + the DB insert through the full server action — heavy and brittle." Every assertion in both files is `IMAGES_SRC.toContain(...)` / `LR_SRC.toMatch(...)` against the raw file text (e.g. `expect(block).toContain('await deleteOriginalUploadFile(savedOriginalFilename)')`), never an actual call to `uploadImages()` or a POST to the LR route.
- Why this is real: this is the mandatory fail-closed guard that keeps a photographer's home/location GPS out of the admin-downloadable original when stripping cannot be guaranteed (CLAUDE.md "Privacy" section, VER-01). It is exactly the kind of privacy-critical logic where "the string is present somewhere in the file" is a materially weaker guarantee than "the function actually deletes the file and rejects the upload when the strip fails." `IMAGES_SRC.search(/stripGpsFromOriginal\(/)` and similar calls locate the FIRST textual occurrence in the whole file — if the guard block is restructured (e.g., delete moved to a shared cleanup helper still referenced elsewhere in the file, or the `continue`/`return` changed so the file is deleted but the DB row is still inserted pointing at the deleted path), the position-based `toBeGreaterThan`/`toContain` checks can still pass while runtime behavior silently regresses to persisting GPS or orphaning a DB row.
- Concrete failure scenario: a refactor consolidates `deleteOriginalUploadFile` calls into one helper invoked slightly later in the function (still inside the 400-char window used by the test, or moved just outside it and picked up because the string appears again elsewhere) — the runtime could insert the image row (with `savedOriginalFilename` still populated) before the delete actually executes, or could no longer set `savedOriginalFilename = null`, causing a later cleanup path to double-free or a race where a concurrent read serves the not-yet-deleted GPS-bearing original.
- Suggested fix: add one real behavior test per path using the existing project convention (mock `stripGpsFromOriginal` from `@/lib/process-image` to resolve `false`, mock the filesystem/DB layer, and call `uploadImages()` / POST the LR route handler): assert the upload is rejected (`gpsStripFailed` error / HTTP 422), no DB row is inserted, and the mocked delete-original function is actually invoked with the saved filename. This directly closes the gap the authors flagged as "heavy and brittle" — but the existing image-queue and topics test suites already show the project's mocking patterns (`vi.mock('@/db', ...)`, `vi.mock('@/lib/process-image', ...)`) scale to exactly this kind of server-action test.

### TEST9-03 — `TopicRouteLockTimeoutError` handling (and its orphaned-image cleanup) has zero test coverage across all 5 catch sites

- Severity: Medium
- Confidence: High
- Location: `apps/web/src/app/actions/topics.ts:15-16` (error class), and catch sites at lines `~187-198` (`createTopic`), `~415-432` (`updateTopic`), `~528-545` (`deleteTopic`), `~595-609` (`createTopicAlias`), `~665-680` (`deleteTopicAlias`). Lock acquisition/timeout itself: `apps/web/src/app/actions/topics.ts:75-90` (`withTopicRouteMutationLock`, `SELECT GET_LOCK(?, 5)` with a 5-second wait).
- Evidence: `grep -rn "TopicRouteLockTimeoutError" src/__tests__/*.test.ts` returns zero matches. `apps/web/src/__tests__/topics-actions.test.ts` (813+ lines) has real, executed-behavior coverage for the route-lock's OTHER failure mode — `RELEASE_LOCK` failure destroying the pooled connection (`:583-611`) and successful serialization (`:547-582`) — but never simulates `GET_LOCK` returning `0`/unacquired, which is exactly what throws `TopicRouteLockTimeoutError`.
- Why this is real: `createTopic` and `updateTopic`'s catch blocks perform real cleanup before returning the user-facing error — `if (imageFilename) { await deleteTopicImage(imageFilename); }` — meaning a lock timeout after a topic-cover image was already processed and saved must delete that now-orphaned file. Since the test suite already has the machinery to mock the lock connection's query responses (used for the RELEASE_LOCK-failure test), the missing case is a one-branch addition, not a heavy behavioral test — this looks like it was simply overlooked when the RELEASE_LOCK-failure test was added, not a deliberate trade-off (unlike TEST9-02).
- Concrete failure scenario: a future refactor moves the `deleteTopicImage(imageFilename)` cleanup out of the `TopicRouteLockTimeoutError` branch (e.g., consolidating it into a single early cleanup that only runs for `SlugConflictsWithRouteError`), and every topic upload made during a lock-contention window silently orphans its processed cover image on disk with no test catching the regression; or the error message mapping (`failedToCreateTopic` / `failedToUpdateTopic` / `failedToDeleteTopic` / `failedToDeleteAlias`) drifts and an admin sees the wrong operation name in a timeout error.
- Suggested fix: in `topics-actions.test.ts`, add a case per action that makes the mocked `GET_LOCK` query resolve with `acquired: 0` (mirroring the existing `RELEASE_LOCK`-failure mock shape) and assert: (a) the action returns the correct localized error key, (b) for `createTopic`/`updateTopic`, `deleteTopicImage` is called with the processed `imageFilename` when one was created, and (c) no DB mutation (insert/update) was attempted.

These don't need admin credentials, so they can run in the default (non-admin) e2e lane.

- Confidence: High
- Location: `apps/web/scripts/backfill-color-pipeline.ts:325-348` (`GET_LOCK(?, 10)` acquisition, `process.exit(1)` on query failure and on `!lockAcquired`).
- Evidence: `grep -rn "process.exit\|lock.*wait" src/__tests__/backfill-color-pipeline.test.ts` returns no matches for these branches. - Suggested fix: extract the lock-acquire-or-bail logic into a small function (e.g. `acquireBackfillLockOrExit(lockConn, lockName)` returning a boolean/throwing a typed error) analogous to `computeBackfillExitCode`, inject a mock connection whose `query()` resolves `{ acquired: 0 }` or rejects, and assert the function signals failure without ever proceeding to the re-encode loop.

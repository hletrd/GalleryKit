### CRIT9-01 — PAT `last_used_at` is still marked before two of three restore-maintenance re-checks in the Lightroom upload route

- Severity: High
- Confidence: High
- Citations: `apps/web/src/app/api/admin/lr/upload/route.ts:94` (entry `isRestoreMaintenanceActive()` check), `:160` (`markAdminAuthTokenUsed(request)` call site), `:182` (`request.formData()`, i.e., the multipart body is not even parsed yet at the mark-used call), `:254-265` (second `isRestoreMaintenanceActive()` re-check, with its own comment explaining why it exists), `:438-452` (third re-check after save/EXIF/GPS-strip); test evidence at `apps/web/src/__tests__/lr-upload-route-behavior.test.ts:293-314`.
- Problem: Cycle 18's WP2 (closing `AGG-C18-10`/`TRC18-01`/`ARCH18-01`) moved `markAdminAuthTokenUsed` to run after the route's **entry** restore-maintenance guard, and the commit message states the explicit directive "Keep PAT usage marks route-admission gated." But the route re-checks `isRestoreMaintenanceActive()` **twice more** downstream of the mark-used call: once at line 259 ("C61-02: re-check restore maintenance after multipart parsing... A restore can begin while a large multipart body is being parsed") and once at line 445 (after save + EXIF + GPS-strip). `markAdminAuthTokenUsed` fires at line 160, before `request.formData()` is even invoked (line 182), so it runs strictly before both later checks. A restore that begins during multipart parsing — the *exact race the C61-02 comment says this second check exists to catch* — still marks the token used, then the request is correctly rejected with 503 moments later. The fix closes the outermost instance of the bug it was written to close and leaves the two inner instances (which are more likely to fire in practice, since multipart parsing of a real photo takes measurably longer than the pre-parse header checks) exactly as broken as before.
- Why the test doesn't catch it: the only regression test for this class of bug, `'rejects with 503 when a restore is in progress (entry guard)'` (line 293), calls `isRestoreMaintenanceActiveMock.mockReturnValue(true)` — a static mock that makes **every** call return `true`, so the very first check at line 94 short-circuits the request before the mark-used call is ever reached. There is no test that returns `false` on the first call and `true` on the second/third call, so the actual bug window (restore starts mid-request) is structurally untestable with the current mock shape and is not exercised.
- Failure scenario: an operator or incident responder treats `admin_tokens.last_used_at` as evidence that a given PAT successfully uploaded (this is exactly the audit use case CLAUDE.md and the original finding describe). A request that races a restore window updates the timestamp and creates no image; the audit trail is misleading in precisely the scenario the fix was supposed to close, just with a narrower and more realistic trigger window (mid-parse instead of pre-parse).
- Suggested fix: either (a) defer the mark-used call until immediately before the DB insert — after all three restore-maintenance checks, topic verification, HDR/GPS gates, and disk-space check — settling it alongside `settleTrackerToActual(true, fileSize)`, or (b) add a second regression test that sequences the mock (`false` then `true`) to prove the C61-02 race is closed, then fix the code to make that test pass.

### CRIT9-02 — CLIP embedding backfill's batch-termination heuristic can silently stop early on skip-heavy corpora, in both the sidecar and the newly-ported server action

- Severity: Medium
- Confidence: Medium-High (verified by static trace and constant inspection; not executed against a live DB fixture)
- Citations: `apps/web/src/app/actions/embeddings.ts:31` (`BACKFILL_BATCH_SIZE = 100`), `:141-211` (new keyset loop), specifically `:168` (`.limit(Math.min(BACKFILL_BATCH_SIZE, remainingEmbeddingBudget))`) and `:211` (`if (pending.length < BACKFILL_BATCH_SIZE) break;`); the identical pre-existing pattern in `apps/web/scripts/backfill-clip-embeddings.ts:159-244`, specifically `:189` and `:244`.
- Problem: Cycle 18's WP3 ported the sidecar's keyset-cursor/attempt-budget pattern into the previously-unwired `backfillClipEmbeddings` server action (closing `AGG-C18-12`), and updated the docs to say `SEMANTIC_SCAN_LIMIT` caps *embedding attempts*, not candidate rows scanned (closing `AGG-C18-13`). Both changes are correct in isolation, but they copied forward a pre-existing boundary bug rather than fixing it: the per-batch query `.limit()` is clamped to `min(BATCH_SIZE, remainingEmbeddingBudget)`, so near the tail of a run (once `attemptedEmbeddings` is within `BATCH_SIZE` of `SEMANTIC_SCAN_LIMIT`) the limit becomes smaller than `BATCH_SIZE`. If the DB still has ≥ that (budget-clamped) number of matching rows beyond the cursor, the fetch returns a "full" page relative to the clamped limit, and `pending.length < BATCH_SIZE` (or `rows.length < BATCH_SIZE` in the sidecar) evaluates true even though the table is **not** exhausted. If that small page happens to contain skip rows (missing `filename_original` or an unresolvable path — the exact condition this fix was designed to route around), the actual number of embedding *attempts* stays well below `SEMANTIC_SCAN_LIMIT`, yet the loop terminates anyway via the trailing `< BATCH_SIZE` heuristic, not via the `attemptedEmbeddings >= SEMANTIC_SCAN_LIMIT` branch. In the sidecar this means the run prints `Done. mode=... processed=X failed=Y` and never logs `Reached SEMANTIC_SCAN_LIMIT (...)`, which is the operator's only documented signal to re-run. In the action it means the return value (`{status:'ok', processed, skipped}`) reports success with no indication that unvisited rows remain past the cursor.
- Why this isn't just theoretical: the CLAUDE.md/README text updated in this same commit says an operator should "repeat the same sidecar command until it finishes without that [SEMANTIC_SCAN_LIMIT] message" — but the scenario above lets the run finish cleanly (no such message) while still leaving valid, embeddable photos never attempted, directly undermining the very runbook guarantee this cycle's docs fix just restated.
- Failure scenario: a gallery with a backlog of rows missing original files (e.g., after a lossy migration, manual file deletion, or a partially-failed restore) runs the production `--force` backfill; near the SEMANTIC_SCAN_LIMIT boundary the run silently exits early, understating how many photos remain un-embedded, with no operator-visible signal that more work is pending.
- Suggested fix: don't infer "end of table" from a short page when the limit itself was budget-clamped. Either (a) always query `BATCH_SIZE` rows and slice/attempt only up to the remaining budget in-process, or (b) after a short page, issue a cheap `EXISTS(... WHERE id > cursor AND ...)` probe to distinguish "truly exhausted" from "budget-limited fetch happened to return a full page." Add a regression test with a backlog where skip-rows sit right at the budget boundary.

## Risks Needing Manual Validation (not confirmed defects)

- **Token-mark coverage is currently single-route, but that's fragile, not verified-safe long-term.** The API-auth refactor in this commit (`apps/web/src/lib/api-auth.ts`) moved `markTokenUsed` out of the shared `withAdminAuth` wrapper entirely and made it the calling route's responsibility via the new exported `markAdminAuthTokenUsed`. Today only one route uses `allowTokenScope` (`apps/web/src/app/api/admin/lr/upload/route.ts:622`), so no route is currently silently losing token-use tracking — but there is no lint/test gate (comparable to `lint:api-auth`) asserting that every future `allowTokenScope` route calls `markAdminAuthTokenUsed` somewhere in its admitted path. A future `lr:read`/`lr:delete`-scoped route could ship without that call and `last_used_at` would simply never update for it, with no test failure to catch the omission. Worth a fixture test scanning for the pairing, analogous to the existing API-auth lint gate, before a second token-scoped route is added.
- **`tag-filter.tsx`'s mobile disclosure renders the full chip list twice in the DOM** (once inside the `<details className="group sm:hidden">` for mobile, once inside the `sm:flex` desktop container, both from the same `chips` JSX constant at lines 137 and 141). At any given viewport only one copy is `display:none`-hidden via Tailwind's `hidden`/`sm:hidden` classes, so this is very unlikely to double-announce to assistive tech, but it does mean every tag chip's click/keydown handlers exist twice per render and the component ships roughly double the interactive DOM nodes it needs. Low confidence this rises to a user-visible defect; flagging only because it's new code from this cycle's WP4 fix and I did not runtime-verify it in a real browser.

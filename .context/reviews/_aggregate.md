## ORCHESTRATOR FIRST-PARTY VERIFICATION (resolving a cross-agent disagreement)

The single highest-severity finding had a **direct contradiction between agents**, so the orchestrator verified it against source + mysql2's own parser before aggregating:

- **code-reviewer (CR-CLIP-01, CRITICAL/High)** and **perf-reviewer (H2, High)** claimed: embeddings are written as base64 into a `MEDIUMBLOB`, but the read path `Buffer.from(row.embedding as string, 'base64')` receives a **Buffer** from mysql2 (not a string), so the `'base64'` encoding arg is ignored, the length check `!== 2048` fails, and **every row is dropped** → semantic search returns `[]` and similar-photos 404s in all cases once enabled.
- **verifier (F1)** and **debugger (DD-2)** claimed the opposite: storage is "self-consistent and functionally correct" (base64 written AND base64 read).

**Orchestrator verdict: code-reviewer + perf-reviewer are CORRECT; verifier/debugger were wrong.** Proof:
1. `mysql2@3.22.0/lib/parsers/text_parser.js:72-73`: `if (charset === Charsets.BINARY) return 'packet.readLengthCodedBuffer()';` — a `MEDIUMBLOB` is charset 63 (BINARY), so mysql2 returns a **Buffer**, not a string, with NO custom `typeCast` configured (`src/db/index.ts` / `scripts/mysql-connection-options.js` confirm none).
2. Empirical Node proof (run this cycle): a 2048-byte float32 buffer → `.toString('base64')` = **2732** chars → stored as the ASCII bytes of that base64 in the blob → mysql2 returns a **2732-byte Buffer** → `Buffer.from(thatBuffer, 'base64')` **ignores the encoding for Buffer input and copies verbatim** → result length **2732 ≠ 2048 (`EMBEDDING_BYTES`)** → `bufferToEmbedding` guard rejects → row filtered out.
3. The write/read are NOT symmetric: write goes `Float32Array → Buffer → base64 string → blob`, but read goes `blob → Buffer (mysql2) → Buffer.from(buf,'base64') [no-op] → wrong length`. The string→string round-trip the verifier assumed never happens because the read value is a Buffer.

This is **latent, not live** (the feature is dark, so no row is ever scanned in production today). It is a CRITICAL-when-enabled correctness defect that is **safely fixable now without activating the feature**.

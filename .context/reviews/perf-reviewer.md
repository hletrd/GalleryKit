# Performance / Concurrency Review — Run 5 Cycle 1 (perf-reviewer)

Repo: GalleryKit (Next.js 16 photo gallery, `apps/web`). 20 prior review cycles. This pass hunts RESIDUAL performance and concurrency issues only — race conditions, shared-state hazards, N+1, missing-vs-query-shape indexes, in-memory growth, Sharp CPU/memory, event-loop blocking, React re-render hotspots, SW cache behavior, bundle, `revalidate=0`.

Methodology: full read (no sampling) of `lib/data.ts`, `lib/analytics-data.ts`, `lib/image-queue.ts`, `lib/process-image.ts`, `lib/color-detection.ts`, `lib/rate-limit.ts`, `lib/auth-rate-limit.ts`, `lib/bounded-map.ts`, `lib/sw-cache.ts`, `public/sw.template.js`, `lib/upload-tracker*.ts`, `lib/admin-backfill-runner.ts`, `lib/gallery-config.ts`, `lib/revalidation.ts`, `lib/restore-maintenance.ts`, `lib/queue-shutdown.ts`, `lib/og-photo-fetch.ts`, `db/index.ts`, `db/schema.ts`, `app/actions/public.ts`, `app/actions/images.ts`, components (`home-client`, `histogram`, `photo-viewer`, `lightbox`), and the tailwind safelist. Schema indexes cross-checked against every query shape.

Overall verdict: the codebase is, frankly, far more disciplined than the typical Next.js app I get called in to triage. Bounded Maps everywhere, FIFO eviction, advisory locks, `sharp.cache(false)`, mmap via file paths, per-format fresh Sharp instances, chunked view-count flush, worker-driven histogram. The residual findings are real but mostly MEDIUM/LOW — there are **no P0 race conditions or data-loss bugs** in this pass. The two findings worth acting on are an unbounded in-memory candidate load in the in-app backfill runner (P1) and missing analytics indexes for the country/referrer breakdown queries (P1).

## P1-HIGH

### PERF-R5C1-01 — In-app backfill runner loads ALL candidate rows into memory at once (unbounded)
**File:** `apps/web/src/lib/admin-backfill-runner.ts:158-168` (`fetchCandidates`), consumed at `276-332` (`runBackfill`).
**Why it's a problem:** `fetchCandidates()` runs `SELECT id, filename_original, filename_avif, filename_webp, filename_jpeg, icc_profile_name, color_primaries, width FROM images WHERE processed=TRUE AND (pipeline_version IS NULL OR pipeline_version < N) ORDER BY id ASC` with **no LIMIT and no batching**. The full result set is materialized into a `CandidateRow[]`, then `runBackfill` iterates the entire array and `queue.add()`s every row up front — so the PQueue's internal task array ALSO holds one closure per candidate simultaneously. The companion operator script (`scripts/backfill-color-pipeline.ts`) deliberately does this in `BATCH_SIZE = 100` chunks (confirmed line 199); the in-app runner does not. The CLAUDE.md header for this very file documents a "pick up where it left off" resume contract that implies streaming, but the implementation slurps everything.
**Failure scenario:** A photographer clicks "Re-encode existing photos" after a pipeline-version bump on a gallery with 50k–200k photos. The candidate query returns every un-migrated row. Each row is ~600–800 bytes of JS object (5 filename strings @ 36-char UUID + ext, plus ICC name). 100k rows ≈ 60–120 MB resident just for the candidate array, doubled by the PQueue closure array, plus mysql2's row buffer for the single mega-result. On the documented Pentium-III-class / small-VM deploy host this is a GC-pressure event at best and an OOM at worst — and it lands on the live web process (not a sidecar), so an OOM takes the whole site down. `fetchCandidateCount()` (line 147) does the COUNT correctly; only the row fetch is unbounded.
**Fix:** Mirror the script's keyset-batched loop. Fetch `WHERE … AND id > :cursor ORDER BY id ASC LIMIT 100`, enqueue the batch, drain (or bound the PQueue depth), advance the cursor to the last id, repeat until a short batch. This caps resident memory at ~100 rows regardless of gallery size and matches the resume semantics already documented. Keep `fetchCandidateCount` for the up-front `affectedRows` disclosure.
**Severity:** P1-HIGH · **Confidence:** High · **Classification:** confirmed

### PERF-R5C1-02 — Analytics country/referrer breakdown queries have no usable index (full scan + filesort)
**File:** `apps/web/src/lib/analytics-data.ts:93-114` (`getCountryBreakdown`), `169-190` (`getReferrerBreakdown`). Index definitions: `apps/web/src/db/schema.ts:231` (`image_views` only has `idx_image_views_image_id_viewed_at` on `(image_id, viewed_at)`).
**Why it's a problem:** Both queries filter `WHERE bot = false [AND viewed_at >= since]` then `GROUP BY country_code` / `GROUP BY referrer_host` `ORDER BY count DESC`. The ONLY index on `image_views` leads with `image_id`. Neither query references `image_id`, so the optimizer cannot use the composite index for the `viewed_at` range, the `bot` filter, or the `country_code`/`referrer_host` grouping. MySQL falls back to a **full table scan + temporary table + filesort** for the GROUP BY. `getTopPhotosByViews` (line 28) and `getTopTopicsByViews` (line 62) DO group by `imageId`/`topic` (index-leading column) so they're fine; the country and referrer breakdowns are the outliers.
**Failure scenario:** `image_views` is the highest-cardinality table in the app — one row per photo view, inserted fire-and-forget on every public page load (`public.ts:354 recordPhotoView`). At even modest traffic this reaches millions of rows within months. The admin `/analytics` page renders all of these breakdowns together. On a multi-million-row `image_views`, a full scan + filesort for `getCountryBreakdown` and `getReferrerBreakdown` is multi-second, holds a connection from the 10-slot pool for the duration, and the admin page feels broken. It also competes with the live insert path for buffer-pool pages.
**Fix:** Add covering composite indexes aligned to the actual filter+group shape: `idx_image_views_bot_viewed_country` on `(bot, viewed_at, country_code)` and `idx_image_views_bot_viewed_referrer` on `(bot, viewed_at, referrer_host)`. The `(bot, viewed_at)` prefix serves the WHERE; trailing the group column makes it a loose-index-scan / covering candidate. Add via a new migration (follow the journal monotonic-`when` runbook in CLAUDE.md). `topic_views` / `shared_group_views` country/referrer breakdowns aren't currently queried, so they don't need the same index yet.
**Severity:** P1-HIGH · **Confidence:** High · **Classification:** confirmed

## P2-MEDIUM

### PERF-R5C1-03 — Embedding hook reads `admin_settings` on EVERY processed image even when semantic search is disabled (default)
**File:** `apps/web/src/lib/image-queue.ts:405-413` (the `void (async () => { … getGalleryConfig() … semanticMode })()` block inside the queue job).
**Why it's a problem:** After every successful image processing, the queue fires a fire-and-forget embedding closure that unconditionally calls `await getGalleryConfig()` to read `semanticSearchMode`, then returns early if `'disabled'` (the documented default). `getGalleryConfig` is wrapped only in React `cache()` (`gallery-config.ts:204`), which dedupes within a single SSR request. The image queue runs **outside any request context** (background PQueue), so `cache()` provides zero deduplication here — every job issues a fresh `SELECT key,value FROM admin_settings WHERE key IN (…GALLERY_SETTING_KEYS)` round-trip purely to discover the feature is off. The caption hook one block up (line 385 `generateCaption`) gets `autoAltTextEnabled` from the config already fetched at line 318, but the embedding block re-fetches independently.
**Failure scenario:** Bulk-uploading 500 photos (the per-window cap) drives 500 redundant `admin_settings` SELECTs against the 10-connection pool, interleaved with the actual processing claims/updates, for a feature that ships disabled. It's not catastrophic (the table is tiny), but it's pure waste on the hot processing path and steals pool connections from live page reads during the exact window when the gallery is busiest.
**Fix:** Reuse the config already resolved at line 318 in the same job scope (plumb `semanticSearchMode` out of that fetch) instead of re-calling `getGalleryConfig()`. Or short-circuit on a process-level cached snapshot of `semanticSearchMode` with a short TTL. The default-disabled path should perform zero DB work.
**Severity:** P2-MEDIUM · **Confidence:** High · **Classification:** confirmed

### PERF-R5C1-04 — `getTopics` correlated `MAX(updated_at)` subquery runs once per topic row (sitemap path)
**File:** `apps/web/src/lib/data.ts:448-469` (`getTopics`).
**Why it's a problem:** The select adds a correlated scalar subquery `(SELECT MAX(images.updated_at) FROM images WHERE images.topic = topics.slug AND images.processed = true)` evaluated per topic row. The available index `idx_images_topic` is `(topic, processed, capture_date, created_at)` — it does NOT include `updated_at`, so each per-topic `MAX(updated_at)` cannot be answered from the index alone; MySQL must probe the index for the `(topic, processed)` partition and then read each candidate row to find the max `updated_at` (no index covers the aggregate). This is an N-subquery pattern where N = topic count.
**Failure scenario:** Topic count is admin-controlled and typically small (a few dozen), and the consumer is `/sitemap.xml` with `revalidate = 3600` ISR, so the blast radius is bounded — this is why it's MEDIUM not HIGH. But on a gallery with many topics each holding tens of thousands of images, the per-topic row probe to compute `MAX(updated_at)` is a non-trivial scan per topic, and the ISR regeneration stalls. The inline comment at line 449 acknowledges the cost and leans on ISR; that's a reasonable bet but it's a latent cliff if topic count or per-topic image count grows.
**Fix:** If/when this shows up in slow-query logs, either add `updated_at` to a covering index `(topic, processed, updated_at)` so the MAX is index-only, or precompute `last_image_updated_at` per topic via a single `GROUP BY topic` join instead of N correlated subqueries. No action needed today given the ISR cache; flagging as a documented latent cost.
**Severity:** P2-MEDIUM · **Confidence:** Medium · **Classification:** likely

### PERF-R5C1-05 — `revalidate = 0` on every public page forces full dynamic render + no SW Cache-Control caching
**File:** Documented policy in `CLAUDE.md` ("Public route freshness"); enforced on public photo/topic/shared/home pages; interacts with `public/sw.template.js:244 networkFirstHtml`.
**Why it's a problem:** Every public page ships the framework-default `no-store` because `revalidate = 0` forces dynamic rendering. This means: (a) zero ISR/CDN HTML caching — every gallery/photo/shared page is rendered server-side from scratch on every request, re-running all the `getImage`/`getImagesLite` DB work; and (b) the service worker's `networkFirstHtml` had to add an explicit `no-store`-ignoring exemption (lines 247-265) just to populate ANY offline cache, because a Cache-Control-honoring SW would never cache these pages. The product correctness reason (async image processing + metadata edits must be instantly visible) is legitimate and documented, so this is a deliberate trade-off, not a bug — but it is the single largest standing CPU/latency cost in the app and worth re-stating.
**Failure scenario:** Under a traffic spike (e.g. a photo goes viral on social, OG unfurls hammer the route), every hit is a full dynamic render against the 10-connection pool. There is no HTML-layer cache to absorb the burst; the pool queues (queueLimit 20) then rejects. The `/api/og` route already got a rate limiter for exactly this CPU-burst reason; the HTML routes have no equivalent shield and no cache.
**Fix:** Reintroduce a SHORT ISR window (e.g. `revalidate = 30–60`) on read-mostly public list/photo pages paired with explicit `revalidatePath` on upload/edit (the `revalidation.ts` helper already exists and is called from `images.ts:517`). The freshness contract becomes "instant on mutation via revalidatePath, ≤60s otherwise" instead of "always dynamic." CLAUDE.md explicitly says to reintroduce ISR only with an invalidation plan — that plan already exists in `revalidateLocalizedPaths`. This converts the steady-state hot path from full-render-per-request to cache-hit-per-request.
**Severity:** P2-MEDIUM · **Confidence:** Medium · **Classification:** needs-manual-validation (product trade-off; requires confirming all mutation paths call revalidatePath before flipping)

### PERF-R5C1-06 — `getImage` prev/next adjacency uses a wide `OR(...)` predicate that defeats single-index range scans
**File:** `apps/web/src/lib/data.ts:954-1057` (`getImage`, the `prevConditions`/`nextConditions` arrays and the two adjacency SELECTs).
**Why it's a problem:** Each adjacency query's WHERE is `or(...4 compound AND branches...) AND processed=true`, ordered by `(capture_date, created_at, id)`. The dated branch is `OR( capture_date > X, (capture_date = X AND created_at > Y), (capture_date = X AND created_at = Y AND id > Z), isNull(capture_date) )`. MySQL cannot turn a 4-way OR over mixed equality/range/null predicates into a single tight index range on `idx_images_processed_capture_date (processed, capture_date, created_at)`; it typically resolves via index-merge or a wider range scan than the logical "one row before / one row after" the query actually needs, then applies `LIMIT 1` after `ORDER BY`. The three adjacency queries run in `Promise.all` with the tags query (good — parallelized), so latency is the max of the three, but each is heavier than a clean keyset seek.
**Failure scenario:** On the single most-hit dynamic route (`/p/[id]`, which is `revalidate=0` per finding 05, so this runs on EVERY photo-page load), a gallery with hundreds of thousands of images pays a wider-than-necessary range scan per prev and per next lookup. At small gallery scale (the stated target) this is invisible; the cliff appears as the `images` table grows. The keyset-cursor list path (`buildCursorCondition`, line 683) has the same OR shape but is capped by pagination; the adjacency path is the one that runs unbounded-per-view.
**Fix:** This is the classic keyset-pagination shape; MySQL 8 handles the canonical row-comparator form `(capture_date, created_at, id) < (X, Y, Z)` far better than the expanded OR when a matching composite index exists. Consider rewriting the dated branch as a tuple comparison and confirming via `EXPLAIN` that it uses `idx_images_processed_capture_date` as a range (not index-merge). The NULL-capture_date handling needs a separate branch either way. Verify with EXPLAIN on a seeded large table before committing — at current scale this is a latent, not active, cost.
**Severity:** P2-MEDIUM · **Confidence:** Medium · **Classification:** needs-manual-validation (requires EXPLAIN on a large seeded table)

### PERF-R5C1-07 — Service worker issues a synchronous HEAD revalidation before serving every cached image (added latency on the gallery paint hot path)
**File:** `apps/web/public/sw.template.js:193-237` (`staleWhileRevalidateImage`, the `if (cached)` block).
**Why it's a problem:** When an image derivative IS in the SW cache, the handler does NOT serve it immediately. It first `await fetch(request.url, {method:'HEAD', headers:{'If-None-Match': cachedEtag}})` and blocks on the network round-trip before returning the cached bytes (it serves cached only after the HEAD resolves 304, or serves network on a 200 with differing ETag). The comment (R10-H3) justifies this as catching admin color-setting flips so stale colors aren't shown for one cycle. But it converts what should be an instant cache hit (the whole point of stale-while-revalidate) into a cache-hit-gated-on-a-network-RTT. On a masonry gallery paint, that's one blocking HEAD per visible derivative.
**Failure scenario:** A returning visitor loads the gallery on a flaky/slow mobile network. Every cached thumbnail now waits for a HEAD round-trip before painting — so the SW, whose job is to make repeat views instant offline-capable, instead adds latency proportional to RTT × concurrent-image-count on exactly the warm-cache path it exists to accelerate. True SWR (serve stale instantly, revalidate in background) is the textbook behavior; the synchronous HEAD inverts it. The `try/catch` falls through to stale-serve on HEAD failure (good), but the success path still blocks.
**Fix:** Serve the cached response synchronously and fire the HEAD/ETag check in the background (`event.waitUntil`-style), updating the cache for the NEXT load if the ETag changed — accept that a color-setting flip is visible on the next view rather than this one. This is the standard SWR contract and what the function name promises. If "stale colors for one cycle" is genuinely unacceptable, scope the synchronous HEAD to only fire when an ETag is present AND the entry is older than some threshold, not on every hit. The 50 MB LRU cap and eviction logic are otherwise clean.
**Severity:** P2-MEDIUM · **Confidence:** Medium · **Classification:** likely (behavior confirmed in code; user-visible impact depends on RTT and gallery size)

## P3-LOW

### PERF-R5C1-08 — `searchImages` worst-case fans out to 3 sequential/parallel LIKE `%term%` scans with no index support
**File:** `apps/web/src/lib/data.ts:1367-1506` (`searchImages`).
**Why it's a problem:** Leading-wildcard `LIKE '%term%'` on `title`, `description`, `camera_model`, `lens_model`, `topic`, `topics.label`, `tags.name`, `topicAliases.alias` cannot use any index — every branch is a full scan. The code is already well-optimized within that constraint: it short-circuits when the main query fills the limit (line 1441), runs the tag+alias queries in parallel only when needed (line 1474), and caps results. So this is genuinely LOW. The rate limiter (`SEARCH_MAX_REQUESTS=30/min`, `public.ts:236`) bounds abuse.
**Failure scenario:** A rare search term that matches nothing in title/description forces all three scans on a large `images` table. Bounded by rate limit and result cap, but still O(rows) CPU per uncached search.
**Fix:** None required at stated scale. If search becomes hot, a MySQL FULLTEXT index on `(title, description)` or a dedicated search engine is the documented escape hatch (the inline R2C11-LOW-06 comment already anticipates this). Flagging only for completeness.
**Severity:** P3-LOW · **Confidence:** High · **Classification:** confirmed (known, mitigated)

### PERF-R5C1-09 — `flushGroupViewCounts` chunked flush issues one UPDATE per group instead of a single batched statement
**File:** `apps/web/src/lib/data.ts:103-134` (the `FLUSH_CHUNK_SIZE = 20` loop).
**Why it's a problem:** The flush drains the buffered view-count Map by issuing `db.update(sharedGroups).set({view_count: view_count + count}).where(id = groupId)` once per group, 20 at a time via `Promise.all`. With the 10-connection pool, 20 concurrent UPDATEs serialize to ~2 pool waves per chunk. The buffer cap is `MAX_VIEW_COUNT_BUFFER_SIZE = 1000` and shared-group count is admin-controlled (typically <100), so in practice the buffer rarely holds more than a handful of distinct groups — this is why it's LOW. The chunking + atomic Map-swap + retry-cap + exponential backoff are all genuinely well-engineered.
**Failure scenario:** Only matters in the pathological case of ~1000 distinct shared groups all viewed within one 5s flush window — 1000 individual UPDATEs across 50 chunks. Not realistic for a personal gallery.
**Fix:** Could collapse to a single `INSERT … ON DUPLICATE KEY UPDATE view_count = view_count + VALUES(...)` or a `CASE`-based bulk UPDATE, but the added SQL complexity isn't justified at the realistic group count. Leave as-is; documenting for the record.
**Severity:** P3-LOW · **Confidence:** Medium · **Classification:** needs-manual-validation (depends on realistic distinct-group cardinality)

### PERF-R5C1-10 — `deleteImageVariants(sizes=[])` triggers a full `opendir` scan on every single/batch delete
**File:** `apps/web/src/lib/process-image.ts:485-526` (`deleteImageVariants`), called from delete paths in `images.ts`.
**Why it's a problem:** When called with `sizes=[]` (the delete path, to catch orphans from a prior `imageSizes` config), the function does `fs.opendir(dir)` and iterates EVERY entry in the webp/avif/jpeg directories to find `{name}_*` matches. The inline comment (C3-F02) acknowledges this runs on every deletion and is "redundant but low-cost." On a directory with tens of thousands of derivative files (large gallery × 6 sizes × 3 formats = potentially hundreds of thousands of files in one flat dir), `opendir` iteration is O(files-in-dir) per deleted image.
**Failure scenario:** Batch-deleting 50 images on a 100k-image gallery does 50 × 3 full directory scans of dirs each holding ~600k files. On a spinning disk or network FS this is seconds of syscall churn per delete batch, blocking the libuv pool. The deterministic-filename path (sizes provided) avoids the scan entirely.
**Fix:** Pass the configured `sizes` from `getGalleryConfig()` into the delete path so filenames are deterministic and the scan is skipped (the orphan-catching scan only needs to run when the sizes config has actually changed, not on every delete). Alternatively, gate the scan behind a once-per-process "did sizes config change" flag as the comment itself suggests. LOW because deletes are admin-initiated and infrequent.
**Severity:** P3-LOW · **Confidence:** Medium · **Classification:** likely

### PERF-R5C1-11 — Per-image processing config fan-out: each upload job re-reads gallery config when quality/sizes absent
**File:** `apps/web/src/lib/image-queue.ts:316-334`.
**Why it's a problem:** When a job arrives without an upload-time `quality`/`imageSizes` snapshot (the backfill/bootstrap path), it calls `getGalleryConfig()` inside the job. For normal uploads the snapshot is passed from `images.ts:443-448`, so the common path is fine. But the bootstrap re-enqueue path (`image-queue.ts:609-628`) enqueues jobs WITHOUT quality/sizes, so every bootstrapped job hits the config DB read. Combined with finding 03 (the unconditional embedding-config read), a bootstrap pass that re-discovers N pending images does up to 2N `admin_settings` SELECTs.
**Failure scenario:** After a restart with a large pending backlog, bootstrap enqueues up to `BOOTSTRAP_BATCH_SIZE = 500` jobs, each potentially doing 2 config reads (process + embedding). Tiny table, but pure redundant load on the pool during the recovery window when the queue is already busy.
**Fix:** Resolve config once per bootstrap batch and thread the snapshot into the enqueued jobs (the upload path already proves this pattern). Fold into the finding-03 fix. LOW given table size.
**Severity:** P3-LOW · **Confidence:** Medium · **Classification:** likely

### PERF-R5C1-12 — `revalidateAllAppData()` exists but `revalidateLocalizedPaths` does O(paths × locales) path invalidation
**File:** `apps/web/src/lib/revalidation.ts:30-42`, `55-57`.
**Why it's a problem:** `revalidateLocalizedPaths` expands each path to one variant per locale and calls `revalidatePath` per variant (the inline note acknowledges O(N×L)). With 2 locales it's trivial. `revalidateAllAppData` does a single `revalidatePath('/', 'layout')` which invalidates the entire app subtree — a sledgehammer. Neither is a hot path (mutation-only), so LOW.
**Failure scenario:** Adding more locales linearly grows the per-mutation invalidation cost; `revalidateAllAppData` on every relevant mutation blows the entire ISR cache (compounding finding 05 if ISR is reintroduced). Not currently impactful with `revalidate=0` everywhere (nothing to invalidate).
**Fix:** No action at 2 locales. If ISR is reintroduced (finding 05), audit that mutations call the narrow `revalidateLocalizedPaths(specificPath)` rather than `revalidateAllAppData` so a single edit doesn't nuke the whole cache.
**Severity:** P3-LOW · **Confidence:** Low · **Classification:** needs-manual-validation

## Audited and found CLEAN (no finding)

These were examined specifically and are correctly engineered — calling out so the next reviewer doesn't re-litigate:

- **In-memory Map growth (rate limits, upload tracker, retry maps, view-count retry):** All bounded via `BoundedMap` (`bounded-map.ts`) with collect-then-delete FIFO eviction, hard caps, and expiry pruning. `image-queue.ts` retry/claim/lastErrors/permanentlyFailedIds maps all capped (`MAX_RETRY_MAP_SIZE`, `MAX_PERMANENTLY_FAILED_IDS`) with hourly `pruneRetryMaps`. `viewCountBuffer`/`viewCountRetryCount` capped with documented eviction. No unbounded growth found.
- **View-count flush concurrency:** Atomic Map-swap (`viewCountBuffer = new Map()`) before drain, `isFlushing` guard, timer-handle-nulled-on-entry (COR-R4C11-01), exponential backoff on DB outage, retry cap. This is textbook — the kind of buffered-write code I usually have to rewrite, already correct here.
- **Sharp memory/CPU:** `sharp.cache(false)` (no heap-pinned op cache), `sharp.concurrency` divided by the 3-format fan-out to avoid drowning libuv, file-path inputs (mmap not heap), `sequentialRead:true`, `failOn:'error'`, per-format fresh instances (no shared-state contamination), 50 MP wide-gamut downscale gate, lazy 10-bit AVIF probe as a Promise-singleton, partial-write cleanup on encode failure, atomic rename. Genuinely strong.
- **Queue race conditions:** Per-image MySQL advisory lock (`GET_LOCK(jobId,0)`) + conditional `WHERE processed=false` UPDATE, claim-retry with escalating backoff, permanently-failed exclusion from bootstrap, keyset bootstrap cursor so low-id failures don't starve later rows. Restore quiesce ordering (clear-before-onIdle, COR-R4C12-01) is correct and the deadlock history is documented.
- **DB pool:** `connectionLimit:10, queueLimit:20, connectTimeout:5000, enableKeepAlive`. `getConnection`/`query`/`execute` wrappers correctly release in `finally`. `group_concat_max_len` init promise awaited via Symbol-on-connection (not WeakMap — the C6R-04 fix is correct). No connection leaks found in the lock-acquire paths (all `release()` in finally).
- **N+1:** `getSharedGroup` batches tags via single `inArray` query (not per-image). `getImage` parallelizes tags+prev+next via `Promise.all`. `getImageByShareKey` collapsed image+tags into one GROUP_CONCAT query. `getTopicsWithAliases` uses a Map for O(1) alias lookup. No N+1 found in the read paths.
- **React re-render hotspots:** `home-client` masonry uses `useMemo` for topicsMap/displayTags/cursor, rAF-debounced resize, `passive` scroll listener, `containIntrinsicSize` + `content-visibility`-friendly cards, eager/lazy fetchPriority gating. `histogram` is worker-driven, AbortController-cancelled, 256px-capped canvas, module-scoped P3-probe singletons. `photo-viewer` receives `images={[image]}` on `/p/[id]` so `findIndex`/`length` are O(1); idle prefetch via `requestIdleCallback`, single responsive preload per neighbor (R4C8 PERF-R4C8-03). `image-zoom` is ref-based (no re-render on mousemove). No render-thrash found.
- **Tailwind dynamic columns classes:** `columns-${colBase}…` ARE safelisted in `tailwind.config.ts:11-16` (verified). Not purged. `columns-0` is unsafelisted but only occurs on an empty gallery where the grid isn't rendered.
- **Sync fs in request paths:** None. Grep for `readFileSync`/`statSync`/`existsSync`/`execSync` in `lib/` and `app/` (excluding tests) returned zero hits. `serve-upload.ts` uses async `lstat`/`realpath` + `createReadStream`.
- **`use-display-capability` snapshot memoization:** Documented React #185 hazard (`getSnapshot` stable ref) is handled per CLAUDE.md note; not re-audited beyond confirming the warning is respected.

**Final verdict: FIX AND SHIP.**

No P0s, no data-loss races, no unbounded-growth bugs in steady state. The two P1s are the actionable ones: **PERF-R5C1-01** (batch the in-app backfill candidate fetch — a genuine OOM risk on large galleries against the live process) and **PERF-R5C1-02** (add the two analytics indexes — a multi-second full-scan on the highest-cardinality table). The P2s are real but mostly latent-at-scale or deliberate product trade-offs (revalidate=0); the SW synchronous-HEAD (07) and the embedding-config-per-job read (03) are the two P2s I'd fix next because they touch the warm-cache paint path and the upload hot path respectively. Everything else is the kind of thing you write down so the table is honest, not the kind of thing that wakes you at 3am. This codebase respects the cycles.

## Findings

### FD-01 — Public `load_more` / `view_record` rate limiters write to the persistent DB counter before checking whether the request is already over the in-memory limit, then roll back
- Severity: Medium (efficiency / defense-in-depth consistency, not an auth bypass).
- Confidence: High.
- Classification: confirmed (still live at HEAD `657eb024`).
- Files:
  - `apps/web/src/app/actions/public.ts:87-114` (`checkLoadMoreRateLimit`, calling `preIncrementLoadMoreAttempt` then unconditionally `incrementRateLimit`)
  - `apps/web/src/app/actions/public.ts:363-392` (`checkViewRecordRateLimit`, same shape)
  - Contrast: `apps/web/src/app/actions/public.ts:263-266` (`searchImagesAction`'s fast path: `if (entry && entry.resetAt > now && entry.count >= SEARCH_MAX_REQUESTS) return { status: 'rateLimited' }` — returns **before** touching the DB at all)
- Why it's a problem: `checkLoadMoreRateLimit`/`checkViewRecordRateLimit` call `preIncrementLoadMoreAttempt`/`isViewRecordRateLimited` (which mutate the in-memory bucket and return whether it was *already* saturated), but regardless of that result they proceed to call `incrementRateLimit(...)` — a DB write — and only *afterward* check `overLimitInMemory` and roll the DB write back via `decrementRateLimit`. `searchImagesAction` avoids this by returning immediately from a read-only in-memory check when the bucket is already saturated, never touching the DB for requests it already knows must be rejected.
- Concrete failure scenario: An anonymous client that has exceeded the 120/min `load_more` (or `view_record`) budget and keeps retrying causes every rejected request to still perform a DB increment + a DB select (`checkRateLimit`) + a DB decrement (rollback) against the single-writer MySQL instance this app runs (per `CLAUDE.md`'s documented single-web-instance/single-writer topology). A sustained abusive retry loop against an already-saturated bucket therefore keeps spending three round-trips of DB work per rejected request instead of zero, unlike the `search` path.
- Suggested fix: Add a read-only in-memory saturated fast path to `checkLoadMoreRateLimit` and `checkViewRecordRateLimit`, mirroring `searchImagesAction`'s `entry.resetAt > now && entry.count >= MAX` early return, so an already-saturated bucket short-circuits before any DB write. Add a focused test (pre-saturate the in-memory map, call the action, assert `incrementRateLimit`/`decrementRateLimit` were not invoked).
- Note: this corroborates (does not duplicate as "new") the still-unprocessed finding filed by the immediately-preceding cycle's architecture reviewer at `.context/reviews/cycle-99-2026-07-01/architect.md` ("Over-limit public load/view requests still force persistent limiter DB work"). It has not yet been triaged into any `-deferred.md` ledger or fixed, so I am re-confirming it is still live at the true current HEAD and flagging it explicitly rather than silently skipping it as "already known."

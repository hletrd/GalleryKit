## DBG8-01 — SQL-restore-scan false-positives a legitimate own-schema `DROP TABLE` split across a chunk-read boundary

- **File/region**: `apps/web/src/lib/sql-restore-scan.ts:35-38` (`ALLOWED_APP_BACKUP_DROP_TABLE_PATTERN`) interacting with `apps/web/src/lib/sql-restore-scan.ts:279-315` (`appendSqlScanChunk`), consumed by the restore scan loop at `apps/web/src/app/[locale]/admin/db-actions.ts:684-719`.
- **Severity**: MED-HIGH (blocks a legitimate DB restore of the app's own backup — a disaster-recovery-critical admin action — with no workaround; false rejection, not a security bypass).
- **Confidence**: High — **confirmed by execution** against the real `sql-restore-scan.ts`.
- **Bug**: The restore file is scanned in `CHUNK_SIZE = 1024*1024` (1 MiB) byte reads. `appendSqlScanChunk` builds `compactedJoin = previousTail + '\n' + chunk` and scans that (plus a small raw bridge) with `containsDangerousSql`. `ALLOWED_APP_BACKUP_DROP_TABLE_PATTERN` (the mask that lets the app's own `DROP TABLE IF EXISTS \`<table>\`;` statements pass, used only inside `stripSqlCommentsAndLiterals*`) matches the table name as a **literal string** with no tolerance for an injected separator inside it. If a 1 MiB chunk boundary happens to land *after* the `TABLE` keyword but *before* the statement's closing `;` (i.e. inside `IF EXISTS \`tablename\`` for one of the 18 `APP_BACKUP_TABLES`), the artificial `\n` inserted by `appendSqlScanChunk` breaks the literal-name match, so the masking regex fails to match the (now-split) statement. Because "DROP" and "TABLE" themselves are NOT split (the boundary is further along, inside the identifier), the raw `/\bDROP\s+TABLE\b/i` dangerous pattern still matches the un-masked text, and `containsDangerousSql` returns `true` even though the statement is a completely legitimate own-schema drop.
- **Trigger**: A real mysqldump backup of the app's own database (produced by `dumpDatabase()`, using `--add-drop-table`) whose byte layout happens to place a `DROP TABLE IF EXISTS \`<one of the 18 table names>\`;` line so that its 1 MiB-aligned chunk boundary falls inside the identifier span (a `~20-30` byte window per statement out of `~40` bytes total, so a rough per-restore probability estimate is on the order of `0.01%–0.1%` for an 18-table schema, but it is **deterministic** for that specific file/size — every retry of the exact same file fails identically).
- **Observable failure**: `restoreDatabase` returns `{ success: false, error: t('disallowedSql') }` ("This dump contains disallowed SQL statements") for a completely valid backup of the app's own schema. There is no operator-visible diagnostic pointing at the real cause, and no documented workaround (the file's byte layout is not something an admin controls).
- **Verification**: Ran a scratch script importing the real `appendSqlScanChunk`/`containsDangerousSql` and feeding it `chunk1 = "DROP TABLE IF EXISTS \`imag"`, `chunk2 = "es\`;\n..."` (simulating the exact boundary split). `containsDangerousSql` on `chunk2`'s combined scan returned `true`, while the SAME content scanned unsplit (`chunk1+chunk2` as one string) returned `false` — confirming the split-dependent false positive. Control cases (unsplit legit `DROP TABLE` for an app table → `false`; `DROP TABLE` for a non-app table → `true`) behaved correctly, isolating the bug to the boundary-split case specifically.
- **Suggested fix**: Either (a) make the raw-bridge reconstruction (already built for the opposite "evasion" direction, C6-01) also feed into the masking pass so a statement that's intact-only-in-the-bridge gets masked before the keyword check runs on `compactedJoin`, or (b) widen the raw bridge window enough to cover the full max statement length and run `hasDisallowedRestoreWriteTarget`/`containsDangerousSql`'s masking against the bridge-reconstructed text *instead of* (not in addition to) the possibly-split `compactedJoin` region for the overlap span, or (c) simplest: extend `ALLOWED_APP_BACKUP_DROP_TABLE_PATTERN`'s masking to tolerate a single injected `\n` between any two characters of the table name (mirroring how `SQL_IDENTIFIER_PATTERN`'s backtick-quoted form already tolerates embedded newlines via `[^\`]`).

## DBG8-02 — Restore's image-queue quiesce has no bounded timeout, unlike every sibling restore drain (can hang a restore forever, holding all locks)

- **File/region**: `apps/web/src/lib/image-queue.ts:1255-1302` (`quiesceImageProcessingQueueForRestore`), called from `apps/web/src/app/[locale]/admin/db-actions.ts:507-509`. Compare with the three sibling drains at `apps/web/src/lib/background-db-writes.ts:90-110` (`drainBackgroundDbWritesForRestore`), `apps/web/src/lib/maintenance-scheduler.ts:62-73` (`drainMaintenanceSweepsForRestore`), and `apps/web/src/lib/admin-mutation-barrier.ts:99-122` (`drainAdminMutationsForRestore`) — all three of which race a `Promise.race([drainPromise, timeoutPromise])` and return `false` on timeout so the caller **aborts** the restore.
- **Severity**: HIGH — contradicts an explicit, tested invariant in the same file (`db-actions.ts:497-506`, comment: *"Each drain either self-limits or races a timeout and ABORTS the restore on timeout (never imports over concurrent writes)"*) and can wedge every future restore/upload/backfill until a manual operator intervention + process restart.
- **Confidence**: High (control-flow read confirms the absence of any timeout wrapper; substantiated further by checking that `embedImageReal`'s CLIP inference call has no timeout on the inference itself — see below).
- **Bug**: `quiesceImageProcessingQueueForRestore` does `queue.pause(); queue.clear(); await queue.onIdle(); await drainQueueSideEffects(state);` with **no timeout race** at all. `queue.clear()` only drops *queued-but-not-started* jobs — it does not cancel an *already-running* task. `queue.onIdle()` therefore waits for whatever job(s) are currently in flight (up to `QUEUE_CONCURRENCY` many) to finish, and `drainQueueSideEffects` waits for the queue's per-job side effects (caption generation, embedding writes) tracked in `state.sideEffects` to settle — including a real CLIP embedding write via `embedImageReal` (`apps/web/src/lib/image-queue.ts:938-965` → `apps/web/src/lib/clip-model.ts`). Inspecting `clip-model.ts:117-173` (`waitForInferenceSlot` / `withInferenceSlot`) shows `CLIP_INFERENCE_QUEUE_TIMEOUT_MS` bounds only the **wait for a free inference slot**, not the actual `await fn()` inference call once a slot is held — a hung/wedged ONNX forward pass (corrupted model weights, native binding issue, resource contention) has no timeout anywhere in the call chain. Similarly, a Sharp encode that hangs (e.g. pathological/adversarial image data, an FS deadlock on a network-mounted upload volume) has no bound either.
- **Trigger**: An admin triggers a DB restore while an image-processing job is in flight (upload just landed and is mid-Sharp-encode, or its post-processing embedding write is mid-CLIP-inference) **and** that in-flight work hangs rather than completing or erroring.
- **Observable failure**: `restoreDatabase()`'s `await quiesceImageProcessingQueueForRestore();` (before `imageQueueQuiesced = true` is even set) never resolves. The whole server action hangs indefinitely: the `LOCK_DB_RESTORE`, `LOCK_COLOR_PIPELINE_BACKFILL`, and `LOCK_SEMANTIC_EMBEDDING_BACKFILL` advisory locks, the upload-processing-contract lock, and the durable restore-maintenance marker (already written by `beginDurableRestoreMaintenance` before the quiesce call) all stay held/active — blocking every future restore, upload, and backfill attempt — until an operator notices, manually clears the durable marker (per the documented `restore:maintenance clear --confirm-clear-restore-maintenance` runbook), and restarts/redeploys the container. This is a materially worse operator experience than the *intended* "abort within N seconds, tell the admin restoreFailed" behavior the three sibling drains implement.
- **Suggested fix**: Wrap `queue.onIdle()` / `drainQueueSideEffects(state)` in the same bounded `Promise.race` pattern as the sibling drains, returning a `false`/timeout signal the caller can use to abort the restore (as CLAUDE.md's own drain-checklist doctrine already requires for every other process-local writer). Consider also adding an inference-level timeout to `embedImageReal`'s `withInferenceSlot(fn)` call so a wedged ONNX forward pass cannot hang indefinitely regardless of caller.

## DBG8-03 — Truncated `iinf` box makes the HEIC/HEIF/AVIF GPS-strip walker silently report "no GPS found" instead of failing closed (privacy-invariant bypass)

- **File/region**: `apps/web/src/lib/gps-exif-strip.ts:430-459` (the `iinf` box parse inside `stripGpsFromIsobmffBuffer`), specifically the `entriesStart` computation at line ~434 and the subsequent `walkChildren(entriesStart, box.dataEnd, 2)` call.
- **Severity**: HIGH — this directly undermines a documented privacy guarantee. CLAUDE.md states: *"Structurally anomalous HEIC/HEIF... FAIL CLOSED... `stripGpsFromOriginal` returns `false`... and both upload paths delete the just-saved original and reject the upload rather than persisting GPS."* This bug instead makes such a file look **clean** (`{ stripped: false }`), so the upload **succeeds** and the original — with its real GPS-bearing EXIF item still embedded — is **persisted to disk** untouched.
- **Confidence**: High — **confirmed by execution** against the real `stripGpsFromIsobmffBuffer`.
- **Bug**: The function already has an explicit `walkAborted` flag (documented at lines 385-393 and 461-469: *"we must not trust a partial walk we did not finish"*) specifically to avoid silently reporting `stripped: false` when a box-level structural anomaly stops the walk before it reaches all Exif/mime items. However, the `iinf` box's `entriesStart = box.dataStart + (version === 0 ? 6 : 8)` is computed and used **without first checking that `box.dataEnd - box.dataStart` actually has room for the version/flags(4) + entry_count(2 or 4) fields**. If an `iinf` box's own declared byte range (valid at the *container* level — it fits within its parent `meta` box) is exactly 4 bytes (i.e. only the FullBox version/flags header, no `entry_count` field at all — a semantically incomplete/truncated `iinf`), then `entriesStart` ends up **past** `box.dataEnd`. The subsequent `walkChildren(entriesStart, box.dataEnd, 2)` generator's loop guard `while (pos + 8 <= end)` is `false` on the very first check (since `pos > end`), so it silently yields **zero** `infe` boxes and returns normally — it does **not** set `walkAborted`. If this is the file's only `iinf` box (the normal case), `exifItemIds.size === 0 && xmpItemIds.size === 0` evaluates `true`, and the function returns `{ buffer: input, stripped: false }` — "no GPS metadata, original is clean" — despite having been structurally unable to enumerate the file's item catalog at all.
- **Trigger**: Any HEIC/HEIF/AVIF file whose `iinf` box is truncated to exactly 4-7 bytes of content (a semantically incomplete but container-level-valid box) — plausible from a corrupted file, an unusual camera/app encoder, or (since only admins can upload, per CLAUDE.md's auth model) an admin uploading such a file with `strip_gps_on_upload` enabled, believing GPS will be stripped.
- **Observable failure**: The upload silently succeeds with the original GPS-bearing bytes persisted verbatim on disk, with no warning to the admin — a silent bypass of an explicit privacy control, in a case the code's own doctrine says should fail closed instead.
- **Verification**: Built a minimal synthetic ISOBMFF buffer (`ftyp` + `meta` containing a 4-byte-content `iinf` box, i.e. `dataEnd - dataStart === 4`, deliberately with a well-formed `infe`/`Exif` declaration that the truncation makes unreachable) and ran it through the real `stripGpsFromIsobmffBuffer`. Result: `{ stripped: false }` — confirming the bypass. (`walkAborted` never fires for this shape.)
- **Suggested fix**: Before computing `entriesStart`, validate `box.dataEnd - box.dataStart >= (version === 0 ? 6 : 8)` for the `iinf` box (mirroring the `dataEnd - dataStart < 4` guard already present one line above it) and set `walkAborted = true; return null;`(or the local equivalent that the R20C20 fix already established) when it does not hold.

## DBG8-04 — `single-writer-guard`'s one-shot boot-time reprobe never re-arms itself, unlike the lapse-recovery loop; log message overstates retry behavior

- **File/region**: `apps/web/src/lib/single-writer-guard.ts:238-269` (`reprobeOnce`), compared with `apps/web/src/lib/single-writer-guard.ts:175-216` (`reacquireOnce`/`scheduleReacquire`), and the shared warning text in `openGuardConnection` at lines 99-112.
- **Severity**: LOW-MED (this is a warn-only diagnostic feature that never blocks/gates anything — CLAUDE.md and the module's own header are explicit that it "cannot enforce single-instance operation"). Still a genuine design-intent violation with an observable (if minor) operator-facing symptom.
- **Confidence**: High that the code behaves this way (deterministic control-flow read); Medium on real-world operational impact given the low blast radius.
- **Bug**: The module's own design intent, per its header comment (`single-writer-guard.ts:37-46`), is that *"a lapse... no longer disarms the guard permanently... schedules an unref'd 60s re-acquire loop."* This self-healing retry loop is real for the **post-acquisition-loss ("lapse")** path: `reacquireOnce()` calls `scheduleReacquire()` on both its "still contended" branch (line 202-207) and its `catch` error branch (line 208-215), so it retries indefinitely. However, the **initial boot-time reprobe** path (`reprobeOnce`, scheduled exactly once, `REPROBE_DELAY_MS = 25s` after a failed boot-time acquisition — see `startSingleWriterGuard` at lines 271-304) has **no equivalent retry scheduling** anywhere in its body: neither the "still contended" branch (line 259-261, `emitLoudTopologyError` then `conn.end()`, no `scheduleReacquire()` call) nor its `catch` branch (line 262-268) nor the `!opened` early return (line 242, when the DB is transiently unreachable at exactly the 25s mark) schedule any further attempt. Once this single reprobe fails for any reason, the guard is permanently inert for the rest of the process's life — it will never later detect that the conflicting instance went away, and will never itself hold/confirm the lock even if it legitimately could from that point on.
- **Secondary symptom**: `openGuardConnection`'s shared warning text (lines 103-109) unconditionally says *"will retry in the background (this does not affect the app)"* for any non-`'startup'` context — which is true for `'re-acquire'` calls but **false** for `'re-probe'` calls, since `reprobeOnce` never schedules a retry on a connect failure either.
- **Trigger**: (a) A rolling deploy whose old process's drain window legitimately exceeds `REPROBE_DELAY_MS` (25s), or (b) a transient DB-connectivity blip that happens to coincide with the one 25-second reprobe attempt.
- **Observable failure**: The operator sees exactly one loud `ANOTHER LIVE GALLERYKIT INSTANCE DETECTED` error (or none, if the connect failure case) at ~25s after boot, and then silence for the rest of that process's lifetime regardless of whether the underlying multi-instance condition later resolves — inconsistent with the "self-heals" narrative the module's own comments describe, and with the sibling lapse-recovery path's actual behavior.
- **Suggested fix**: Have `reprobeOnce`'s contended and error/connect-failure branches call `scheduleReacquire()` (or an equivalent bounded retry) just like `reacquireOnce` does, so the boot-time-failed-acquisition path gets the same indefinite retry semantics the header comment already promises. Separately, adjust `openGuardConnection`'s warning text to not claim background retry for the `'re-probe'` context unless that context is actually wired to retry.

## DBG8-05 (LOW, minor/cleanup-class findings)

1. **`dirname()` off-by-one boundary in `restore-maintenance-durable.ts:11-14`**: `Math.max(filePath.lastIndexOf('/'), filePath.lastIndexOf('\\'))`; the caller only treats a positive result (`slash > 0`) as a valid split point, so a path with a **single leading slash and no other separator** (e.g. `/marker.json`, where `lastIndexOf('/') === 0`) incorrectly falls through to `'.'` instead of `'/'`. Currently only reachable via the `NODE_ENV === 'test' && RESTORE_MAINTENANCE_MARKER_PATH` branch (`restore-maintenance-durable.ts:16-22`), so practical impact is limited to test fixtures that happen to use a bare-root path (unlikely in practice — most test paths include a temp-dir prefix). Confidence: Medium (real boundary bug by inspection, not executed). Severity: Low.

2. **A handful of `fs` calls in `runRestore` (`apps/web/src/app/[locale]/admin/db-actions.ts:684-719`, the tail-scan file-open/read block and the chunked dangerous-SQL scan loop) are not wrapped in a `catch` that returns the typed `RestoreResult`** — unlike nearly every other step in the same function. A rare `fs.stat`/`fs.open`/`fd.read` error at exactly these points propagates as an **uncaught rejection** out of the `'use server'` action instead of the graceful `{ success: false, error: t('restoreFailed') }` shape used everywhere else. Resource cleanup itself is *not* affected — the surrounding `finally` blocks (temp-file cleanup, fd close, lock release, maintenance-marker clear) all still run correctly because `finally` executes regardless of whether the try body threw or returned, and `restoreLifecycleVerified`/`keepRestoreMaintenance` default to `false`, which the outer finally logic already handles as "safe to end maintenance." The only user-visible difference is an inconsistent/ungraceful error shape reaching the client for this narrow class of failures (e.g., a raw digest error instead of a translated toast). Confidence: Medium (control-flow read; not executed). Severity: Low.

3. **`searchImages` tag_names parity (`apps/web/src/lib/data.ts:1600-1750`) — already known, not counted as new.** The main title/description/camera/lens/topic-match branch and the topic-alias-match branch both hard-code `tag_names: NULL` (`searchFieldsWithNoTags`), so an image found via those paths (rather than a tag match) falls back to a generic "Photo #id" result label/aria-name instead of a tag-derived one when it has no meaningful title. This is the **exact** tradeoff explicitly called out and consciously deferred in commit `cc46b1d69c11` ("fix(a11y): preserve meaningful result labels"), whose commit message states: *"Rejected: Widening public search result selects with tag_names or alt_text_suggested | useful later, but not needed to fix the confirmed filename-like title bypass without changing public query shape."* Flagging here only for completeness per the task brief's explicit mention of "searchImages tag_names parity" — not a new finding.

# designer review — cycle 6

## Summary (2-4 lines)

Static source review of the GalleryKit web UI (Next.js 16 App Router, React 19, Tailwind, Radix/shadcn) against committed HEAD `583277fb`, focused on WCAG 2.2, keyboard operability, forms/loading/error UX, dark/light mode, i18n, and perceived performance. This codebase has already been through 90+ prior review cycles and the public/admin UI is unusually well hardened (touch targets, focus-visible rings, reduced-motion suppression, live regions, focus traps, canvas accessible names, and computed-contrast comments are already in place almost everywhere I checked). I found 3 genuinely new, concrete issues rather than re-treading well-covered ground: toast notifications have no close button and a fixed 4-second auto-dismiss with no keyboard-focus pause; admin data tables never set `scope="col"` on header cells; and several truncated metadata values expose their full text only via a mouse-hover native `title` tooltip with no keyboard/touch equivalent. No CRIT/HIGH findings; all three are MED or LOW.

## Findings

### F1 — Toast notifications auto-dismiss in 4s with no close button and no keyboard-focus pause [SEV: MED | CONF: High | apps/web/src/components/ui/sonner.tsx:13-37, apps/web/src/app/[locale]/layout.tsx:149]

**Problem:** `<Toaster />` is rendered once in the root layout (`apps/web/src/app/[locale]/layout.tsx:149`) with no props, and `apps/web/src/components/ui/sonner.tsx:13-37` forwards no `closeButton`, `duration`, or `toastOptions` override either. I confirmed in the installed `sonner@2.0.7` package (`node_modules/sonner/dist/index.mjs:417`) that the library default lifetime is `TOAST_LIFETIME = 4000` (4 seconds), and that a per-toast/per-Toaster `closeButton` is required to render the dismiss `<button>` (`dist/index.mjs:466-473, 779-787`) — since this app never sets it, **no toast in the entire product has a close/dismiss control.** I also traced the auto-dismiss pause logic (`dist/index.mjs:582-604`): the timer only pauses on `expanded` (mouse hover over the toast list) or `interacting` (`onPointerDown`), and `onFocus`/`onBlur` (`dist/index.mjs:1109-1124`) only track focus-within for a *different* purpose (restoring the previously-focused element on toast dismissal) — keyboard Tab-focus into the toast region does **not** pause the countdown the way mouse hover does. A grep across the app confirms zero `duration:` or `closeButton` overrides anywhere in `src/` (only unrelated `closeButtonRef` variables in `lightbox.tsx`/`info-bottom-sheet.tsx` matched).

I also confirmed the SC 4.1.3 half is fine — the toast list does carry `"aria-live": "polite"` (`dist/index.mjs:1084`), so screen readers are told a status message appeared. The gap is purely about *time to read/act*, not announcement.

**Failure scenario:** An admin uploads a batch of RAW/HDR photos. `apps/web/src/components/upload-dropzone.tsx:302,316,331,335` can fire up to four separate `toast.warning(...)` calls back-to-back for one upload (`warningSuccess`, `partialSuccess`, `hdrWarning`, `wideGamutDownscaleWarning`), each independently timed to vanish in 4 seconds, stacking on top of each other. A low-vision, dyslexic, or simply slower reader cannot finish reading toast 1 before toasts 2-4 have already appeared and toast 1 has started disappearing, and there is no button to keep it open or scroll back to it. Similarly, `apps/web/src/app/[locale]/admin/(protected)/db/page.tsx:66` does `toast.error(`${t('errorBackup')}: ${result.error}`)` — a raw, unbounded server error string describing a failed database backup — which can be arbitrarily long/technical and disappears after 4 seconds with no way to recover it except retrying the destructive action. `apps/web/src/components/image-manager.tsx:514` similarly loops `res.warnings.forEach(w => toast.warning(w))`, so a bulk-tag operation with several warnings queues several independently-expiring toasts.

**Fix:** Pass `closeButton` to the root `<Toaster />` (or set it per-toast for error/warning calls at minimum) so every toast has a persistent, keyboard-reachable dismiss affordance; consider a longer `duration` (or `Infinity`) specifically for `toast.error`/`toast.warning` calls that carry dynamic/unbounded text (server error strings, per-file warning lists), while leaving short fixed-string success toasts at the default. This is a one-line Toaster prop plus a handful of call-site duration overrides, not an architectural change.

### F2 — Admin data tables never set `scope="col"` on header cells [SEV: LOW-MED | CONF: High | apps/web/src/components/ui/table.tsx:68-79, apps/web/src/components/image-manager.tsx:428-448, apps/web/src/app/[locale]/admin/(protected)/categories/topic-manager.tsx:231-236, apps/web/src/app/[locale]/admin/(protected)/tags/tag-manager.tsx:100-102]

**Problem:** The shared `TableHead` primitive (`apps/web/src/components/ui/table.tsx:68-79`) renders a real `<th>` (good — it isn't a styled `<div>`), but neither the primitive nor any of its three real data-table call sites ever pass `scope="col"`. I checked every `<TableHead>` usage in the admin surface: the Image Manager's 9-column table (`image-manager.tsx:428-448` — select-all, preview, title, filename, topic, tags, gamut, date, actions), the Categories/topic table (`topic-manager.tsx:231-236` — order, label, slug, aliases, map-visible, actions), and the Tags table (`tag-manager.tsx:100-102` — name, count, actions). None of the 18 `<TableHead>` elements across these three tables sets `scope`.

**Failure scenario:** These are all simple single-header-row tables with no row/column spans, so most modern screen readers' table-navigation heuristics (NVDA/JAWS/VoiceOver table mode) will usually still infer the right header for a cell — but that inference isn't guaranteed across AT/browser combinations, and it is exactly the case WCAG's technique H63 ("Using the scope attribute to associate header cells and data cells in data tables", supporting SC 1.3.1 Info and Relationships) exists to make explicit rather than implicit. An admin navigating the Image Manager table with a screen reader's cell-by-cell/table-navigation shortcut (not just linear reading) is the concrete audience affected; today they depend entirely on AT heuristics rather than markup.

**Fix:** Add `scope="col"` as the default in the shared `TableHead` component (`ui/table.tsx:68-79`), e.g. `<th scope="col" ...>` unless a caller explicitly overrides `scope` via props — this fixes all three tables (and any future one built on the primitive) in a single place rather than requiring each call site to remember it.

### F3 — Truncated metadata (camera/lens model, filenames) is only recoverable via mouse-hover `title`, with no keyboard/touch equivalent [SEV: LOW-MED | CONF: Medium | apps/web/src/components/info-bottom-sheet.tsx:413,419, apps/web/src/components/photo-viewer.tsx:806,812, apps/web/src/components/image-manager.tsx:494, apps/web/src/components/upload-dropzone.tsx:537]

**Problem:** Several places render CSS-truncated (`truncate` / `max-w-[...]`) text and rely solely on the native HTML `title` attribute to expose the full value on mouse hover:
- `info-bottom-sheet.tsx:413`: `<dd className="font-medium truncate" title={nu(image.camera_model)}>{image.camera_model}</dd>` and `:419` (lens model) — same pattern in the public photo viewer's mobile bottom sheet.
- `photo-viewer.tsx:806,812`: identical camera/lens model `<dd title={...}>` pattern in the desktop sidebar Color/EXIF details.
- `image-manager.tsx:494`: `<TableCell className="... truncate" title={image.user_filename || image.filename_avif}>` for the admin filename column.
- `upload-dropzone.tsx:537`: `<p className="font-medium truncate text-xs" title={file.name}>{file.name}</p>` for the in-progress upload file-name row.

None of these elements is a link, button, or otherwise focusable/interactive element (no `tabIndex`, no `role`), so there is no way to reach them via keyboard to trigger any focus-based reveal, and touchscreen users get no long-press/tap equivalent either (native `title` tooltips are a mouse-hover-only affordance in effectively all mobile browsers and are unreliable even on desktop touchscreens).

**Failure scenario:** A photographer using only a keyboard (or a touchscreen tablet) opens a photo whose lens name is long enough to truncate (e.g. `"EF 100-400mm f/4.5-5.6L IS II USM"` style strings are common) in the sidebar Color/EXIF panel, or an admin reviewing the Image Manager table for a photo with a long original filename. They see `...` at the end of the value and have no way to read the rest of it — a mouse user hovering the same row does. This is a real (if narrow) information-access gap rather than a strict single-SC violation, since the full text *is* present in the DOM for screen-reader users reading linearly (the `title` doesn't replace the accessible name here); it specifically affects sighted keyboard-only and touch-only users.

**Fix:** For the camera/lens `<dd>` values, either stop truncating (these are short single-line fields, so `whitespace-normal`/wrap may be acceptable), or wrap them in the existing `Tooltip`/`TooltipTrigger` primitive (already used elsewhere in this app, e.g. `histogram.tsx:702-714`) on a focusable element so keyboard users get the same reveal Radix's Tooltip already provides on focus. For the Image Manager filename cell and the upload file-name row, the same Tooltip wrap, or an expand-on-click affordance, would close the gap without giving up the truncated layout.

## Final sweep (commonly-missed) notes

- **Character-key keyboard shortcuts** (`photo-viewer.tsx:410-427`, `lightbox.tsx:338-346` — bare `c`/`h`/`f`/`i`/space without a modifier) are WCAG 2.1.4 territory, but both call sites already guard with `isEditableTarget(e)` (`lib/editable-target.ts`, with an explicit `COR-R4C6-12` fix noted in `lightbox.tsx:320-324` for the space-key/typing conflict), and the shortcuts are only live while the full-screen viewer/lightbox is the active UI. I did not file this as a new finding — it reads as a previously-considered, deliberately-scoped design, not an overlooked gap.
- **The `/map` route's Leaflet map** (`components/map/map-client.tsx`) renders markers with no `alt`/`title` option passed to `<Marker>`, so Leaflet's default marker icon gets an empty accessible name. I checked whether this is a real gap and found the page already ships a full parallel accessible alternative: `app/[locale]/(public)/map/page.tsx:80-110` renders a "skip to photo list" link, an `aria-describedby` map region explaining a text alternative exists, and a complete `<ul aria-label>` of the same markers as real `<Link>`s. Given that equivalent, keyboard/AT-operable path already exists next to the map, I did not file the bare Leaflet marker labels as a standalone finding.
- I checked for chart/graph components in the admin Analytics page (`analytics-client.tsx`) since data-viz elements are a common a11y miss; there are none — analytics render as plain tables/lists, so no chart-accessible-alternative gap exists.
- I checked `histogram.tsx` (a `<canvas>`-based data visualization) specifically for a missing accessible name/summary, since canvases are a classic miss; it already has `role="img"` plus a descriptive `aria-label` that includes the current channel mode, plus separate text rows for clip percentages and a tooltip-explained key-type classification. No finding.
- I re-verified (rather than re-filing) the two already-known cycle-10 items relevant to this angle: the Timeline/Year-archive duplicate-accessible-name issue (`AGG-C10-15` / `DSGN10-MED-01`) and the tag-context-free search result labels (`AGG-C10-16` / `UIUX-C10-01`). Both `timeline/page.tsx` and `year/[year]/page.tsx` are on this cycle's peer-dirty list (a second session is actively editing them), so per the briefing I did not re-verify their current byte-for-byte state or propose edits; I confirmed only that these are the same already-tracked findings, not new ones.
- I checked `globals.css` color-token definitions; the file already carries computed-contrast-ratio comments for the tokens I spot-checked (e.g. `--muted-foreground` on `--background` in both light and dark/OLED themes), consistent with prior cycles' contrast work, so I did not attempt to re-derive contrast ratios for the full token set without stronger evidence of a specific regression.
- I looked for missing `alt` text, `role="button"` without `tabIndex`/keydown handling, and un-gated `autoFocus` across all listed components; the only `autoFocus` in the app is on the admin login form's username field (`login-form.tsx:73`), a conventional and accepted pattern for a single-purpose login page.

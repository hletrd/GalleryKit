## Findings

### PERF-C36-01 - Bootstrap orphan-temp cleanup repeats on every queue continuation

- Severity: Medium
- Confidence: High
- Evidence: `bootstrapImageProcessingQueue()` scans up to `BOOTSTRAP_BATCH_SIZE = 500` pending rows per pass (`apps/web/src/lib/image-queue.ts:80`, `apps/web/src/lib/image-queue.ts:925`, `apps/web/src/lib/image-queue.ts:946`) and schedules another pass after `state.queue.onIdle()` when the batch is full (`apps/web/src/lib/image-queue.ts:885`, `apps/web/src/lib/image-queue.ts:1007`, `apps/web/src/lib/image-queue.ts:1010`). At the end of every pass it launches both orphan cleanup scans (`apps/web/src/lib/image-queue.ts:1013`, `apps/web/src/lib/image-queue.ts:1017`). `cleanOrphanedTmpFiles()` reads all entries in the WebP/AVIF/JPEG upload directories (`apps/web/src/lib/image-queue.ts:33`, `apps/web/src/lib/image-queue.ts:41`), and `cleanOrphanedTopicTempFiles()` reads the topic temp/resource directories (`apps/web/src/lib/process-topic-image.ts:135`, `apps/web/src/lib/process-topic-image.ts:142`).
- Failure scenario: after a restart with a large unprocessed backlog or a size/pipeline reconfiguration, each 500-image continuation re-scans every upload/resource directory. A 10k-image backlog means roughly 20 bootstrap passes, so the process can issue 100 full directory reads before the queue is fully bootstrapped. These cleanup promises are also fire-and-forget, so a slow filesystem can overlap cleanup I/O with image processing and the next continuation, increasing startup latency and disk pressure on the already disk-constrained deploy host.
- Fix: gate orphan cleanup separately from continuation batches, for example `orphanCleanupRun` or a tracked cleanup promise, and run it once per process startup/restore resume rather than per bootstrap batch. If repeated cleanup is desired, schedule it on the existing hourly GC cadence (`apps/web/src/lib/image-queue.ts:1039`, `apps/web/src/lib/image-queue.ts:1048`) instead of tying it to backlog size.

### PERF-C36-02 - Per-photo OG generation cannot 304 unchanged revalidations

- Severity: Medium
- Confidence: High
- Evidence: the per-photo OG route performs DB/config reads (`apps/web/src/app/api/og/photo/[id]/route.tsx:58`, `apps/web/src/app/api/og/photo/[id]/route.tsx:63`), internal derivative fetches (`apps/web/src/app/api/og/photo/[id]/route.tsx:118`, `apps/web/src/app/api/og/photo/[id]/route.tsx:122`), Satori rendering (`apps/web/src/app/api/og/photo/[id]/route.tsx:134`, `apps/web/src/app/api/og/photo/[id]/route.tsx:221`), and Sharp JPEG post-processing (`apps/web/src/app/api/og/photo/[id]/route.tsx:223`, `apps/web/src/app/api/og/photo/[id]/route.tsx:229`) but emits only `Content-Type` and `Cache-Control`. The sibling topic OG route already computes an input hash and returns `304` on `If-None-Match` before the image pipeline (`apps/web/src/app/api/og/route.tsx:118`, `apps/web/src/app/api/og/route.tsx:133`).
- Failure scenario: after `max-age`/`s-maxage` expiry, crawler/CDN/browser revalidation of popular photo share URLs reruns the full DB + internal fetch + Satori + Sharp path even when the photo, title, and SEO settings are unchanged. The 30/min/IP limiter bounds a single abusive source, but it does not reduce normal distributed crawler revalidations across many photo URLs.
- Fix: add an `ETag`/`If-None-Match` contract to `api/og/photo/[id]` before derivative fetch and Satori work. Include all render-affecting inputs in the hash: image id, title/display title inputs, `filename_jpeg`, `updated_at` or equivalent image mutation signal, site title/SEO values, configured `imageSizes`, and the image pipeline/settings version that should invalidate a derivative re-encode. Return the same cache-control plus `ETag` on both `200` and `304`.

### PERF-C36-03 - CLIP image preprocessing ignores the repository's tunable input-pixel cap

- Severity: Low
- Confidence: Medium
- Evidence: the main image pipeline exposes `MAX_INPUT_PIXELS` from `IMAGE_MAX_INPUT_PIXELS` and applies it to upload metadata validation and later processing (`apps/web/src/lib/process-image.ts:352`, `apps/web/src/lib/process-image.ts:357`, `apps/web/src/lib/process-image.ts:922`, `apps/web/src/lib/process-image.ts:1104`, `apps/web/src/lib/process-image.ts:1126`). `embedImageReal()` decodes originals through `sharp(imagePath, { autoOrient: true })` without passing that project cap (`apps/web/src/lib/clip-model.ts:273`, `apps/web/src/lib/clip-model.ts:290`). The callers include queue-side embedding after processing (`apps/web/src/lib/image-queue.ts:353`, `apps/web/src/lib/image-queue.ts:392`), the admin action (`apps/web/src/app/actions/embeddings.ts:155`, `apps/web/src/app/actions/embeddings.ts:160`), and the operator backfill script (`apps/web/scripts/backfill-clip-embeddings.ts:185`, `apps/web/scripts/backfill-clip-embeddings.ts:190`). Sharp 0.34.5 still has its own default pixel guard, so this is not an unbounded decode; the gap is that lowering `IMAGE_MAX_INPUT_PIXELS` for this deployment does not constrain the CLIP path.
- Failure scenario: an operator lowers `IMAGE_MAX_INPUT_PIXELS` to fit host memory, or a legacy original predates the current upload validator. New uploads and derivative generation honor the lower cap, but production CLIP backfill can still attempt to decode a much larger existing original up to Sharp's default limit, causing a native-memory spike inside the web process or sidecar. `CLIP_INFERENCE_CONCURRENCY` bounds concurrent embeddings, but it does not enforce this per-image memory budget.
- Fix: share the same cap with CLIP preprocessing, or add a CLIP-specific `CLIP_IMAGE_MAX_INPUT_PIXELS` that defaults to `MAX_INPUT_PIXELS`, and pass it to Sharp in `embedImageReal()`. Add a small contract test or source test that keeps the CLIP constructor options aligned with the image pipeline's deployment cap.
